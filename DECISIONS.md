## 1. 2026-07-01 – Use Clean Architecture
**Status**: Accepted
**Context**: The project aims to evolve into a multi‑tenant SaaS with many independent domains (WhatsApp, AI, CRM, analytics). A clear separation of concerns is required to keep the codebase maintainable.
**Decision**: Adopt Clean Architecture with four concentric layers (Presentation, Application, Domain, Infrastructure). All external frameworks (Express, Next.js, Prisma) live in the outermost layer.
**Consequences**:
- Guarantees low coupling and high testability.
- Slightly higher initial boilerplate.
- Enforces dependency direction via explicit interfaces.

## 2. 2026-07-01 – Choose TypeScript over JavaScript
**Status**: Accepted
**Context**: The team consists of TypeScript‑savvy engineers; the codebase will handle complex data models and external APIs.
**Decision**: Use TypeScript with `strict` mode enabled for both frontend and backend.
**Consequences**:
- Increased compile‑time safety.
- Requires proper tooling (tsc, ESLint) but improves developer confidence.

## 3. 2026-07-01 – Store WhatsApp session via Puppeteer (QR login) initially
**Status**: Accepted (with migration path)
**Context**: The WhatsApp Cloud API requires a verified Business account, which is not available during MVP.
**Decision**: Implement a Puppeteer‑based WebSocket client that logs in via QR code. Abstract the provider behind an `IWhatsAppProvider` interface.
**Consequences**:
- Faster MVP delivery.
- Future migration to Cloud API will be straightforward (swap implementation).

## 4. 2026-07-01 – Use BullMQ + Redis for background jobs
**Status**: Accepted
**Context**: Campaign scheduling, message retries, and AI reply generation are asynchronous and need reliability.
**Decision**: Adopt BullMQ (built on Redis) for its robust API, built‑in retries, and rate limiting capabilities.
**Consequences**:
- Requires Redis cluster for production scaling.
- Provides easy monitoring via Bull Board.

## 5. 2026-07-01 – Adopt PostgreSQL with Prisma ORM
**Status**: Accepted
**Context**: Relational data with strong integrity constraints (multi‑tenant isolation, foreign keys) is needed.
**Decision**: Use PostgreSQL as the primary data store, accessed via Prisma for type‑safe queries and migrations.
**Consequences**:
- Can leverage PostgreSQL's RLS for tenant isolation.
- Adds an extra abstraction layer but simplifies schema evolution.

## 6. 2026-07-01 – Store PII encrypted at rest using pgcrypto
**Status**: Accepted (com desvio pontual registrado na ADR #21)
**Context**: GDPR/CCPA compliance requires personal data to be encrypted.
**Decision**: Encrypt `phone`, `message.content`, and any other PII columns using `pgp_sym_encrypt`/`pgp_sym_decrypt`.
**Consequences**:
- Slightly higher CPU usage for encryption/decryption.
- Must manage encryption keys securely via vault.
- **Nota (2026-07-06)**: para segredos de credenciais por tenant (`TenantCredential`, Milestone 1), a ADR #21 optou por criptografia em nível de aplicação (AES-256-GCM, `Cipher`/`AesGcmCipher`) em vez de `pgcrypto`, por portabilidade e testabilidade — desvio deliberado e localizado a esse model, não uma reversão desta ADR para PII em geral (`phone`/`message.content` continuam no escopo original desta decisão).

## 10. 2026-07-01 – Escolha da Tecnologia de Integração WhatsApp
**Status**: Accepted
**Context**: Precisamos conectar ao WhatsApp de modo que o usuário possa escanear um QR Code, manter a sessão persistente e reconectar automaticamente. As opções avaliadas foram:
- **WhatsApp Cloud API** – oficial, mas requer Business Account verificado, tem limites de uso e não gera QR Code diretamente; exige webhook.
- **Evolution API** – solução de terceiros, documentação limitada, custos incertos e dependência externa.
- **Baileys** – biblioteca Node que implementa o protocolo WhatsApp Web, gera QR Code, tem comunidade ativa, documentação clara e possibilita persistência de estado.

**Decisão**: Utilizar **Baileys**.
**Justificativa**:
- **Estabilidade**: Baileys tem sido usada em produção por diversas startups, recebendo atualizações frequentes.
- **Manutenção**: Código‑aberto, comunidade ativa, issues bem gerenciadas.
- **Documentação**: README completo com exemplos de QR Code, eventos de conexão e reconexão.
- **Escalabilidade**: Permite múltiplas sessões (para SaaS future) e pode ser horizontalizada usando containers.
- **Facilidade de desenvolvimento**: API simples (`makeWASocket`), callbacks (`'qr'`, `'connection.update'`).
- **Limitações**: Não é oficialmente suportado pelo WhatsApp (risco de bloqueio), porém suficiente para o MVP.
- **Compatibilidade SaaS**: A camada de abstração (`IWhatsappProvider`) permite troca futura para Cloud API sem impactar o resto do código.

**Consequências**:
- Necessário armazenar o estado de autenticação (arquivo JSON) de forma criptografada.
- Implementar reconexão automática usando o estado salvo.
- Adicionar dependência `baileys` ao `apps/api/package.json`.

## 11. 2026-07-06 – Adiar migração do domínio Conversations até conclusão da Milestone 1
**Status**: Accepted
**Context**: Uma auditoria de integração revelou uma segunda árvore de código completa e não documentada (`src/`, `tests/`, `specs/M003-Conversations.md`, com seu próprio `prisma/schema.prisma`) implementando um domínio de Conversas WhatsApp (Contact, Conversation, Message, Attachment, Tag, InternalNote, ConversationEvent), totalmente desconectada da arquitetura oficial (`apps/api` + `apps/dashboard`) e nunca referenciada em `ROADMAP.md`. A auditoria confirmou, via busca cruzada de referências, que não existe nenhuma dependência de código entre essa árvore e o que está sendo construído na Milestone 1 (WhatsApp Connectivity).
**Decisão**: A migração do domínio Conversations foi adiada para após a conclusão da Milestone 1, a fim de reduzir risco arquitetural e evitar misturar refatoração estrutural com desenvolvimento de novas funcionalidades. A árvore `src/` passa a ser tratada temporariamente como código legado, preservada apenas como referência técnica. A arquitetura oficial do projeto continua sendo exclusivamente `apps/api` + `apps/dashboard`. Durante a implementação da M1: não mover arquivos de `src/`; não alterar `specs/M003-Conversations.md`; não modificar o schema legado (`prisma/schema.prisma`, seção Conversations); não fundir as duas arquiteturas; usar o código legado apenas como referência quando houver lógica reaproveitável.
**Consequências**:
- Reduz o risco de misturar migração estrutural com entrega de funcionalidade nova (M1).
- `prisma/schema.prisma` passa a ser compartilhado por dois domínios até a consolidação: a seção legada (Conversations, intocada) e a nova seção (WhatsApp Connectivity, adicionada a partir do Item 2 da M1). Isso exige cuidado para não colidir nomes de model/enum entre as duas seções.
- A auditoria completa (inventário, comparação, plano de consolidação em 7 seções) permanece registrada na conversa e deverá ser retomada como primeira tarefa após a conclusão da M1.

## 12. 2026-07-06 – Canal assíncrono no port `WhatsAppProvider` (`onStatusChange`)
**Status**: Superseded pela ADR #14 (Architecture Gate Review, achado F2) — `onStatusChange`/`WhatsAppProviderStatusUpdate` foram substituídos por `onEvent`/`WhatsAppProviderEvent`. Mantido aqui como registro histórico da decisão original; não reflete mais o código atual.
**Context**: Antes de implementar o `BaileysProvider` (M1, Item 3), foi feita uma revisão arquitetural do port `WhatsAppProvider`. Baileys é orientado a eventos (`sock.ev.on('connection.update', ...)`) — pareamento confirmado, QR gerado e quedas de conexão chegam de forma assíncrona, sem que a Application tenha chamado nada. O port existente só expunha métodos síncronos de pull (`connect`, `getStatus`, `getQRCode`), o que forçaria polling ou uma mudança de contrato assim que o Baileys real fosse integrado.
**Decisão**: Adicionar `onStatusChange(listener)` ao port `WhatsAppProvider`, com um novo tipo de Domain `WhatsAppProviderStatusUpdate`. `SessionManager` assina esse canal logo após conectar/reconectar e persiste as mudanças recebidas. Um único listener por instância de provider (substitui, não acumula) — cada `WhatsAppProvider` corresponde a exatamente um socket/sessão neste escopo.
**Consequências**:
- `BaileysProvider` (Item 3) já nasce com um contrato compatível com o modelo assíncrono real do Baileys, sem retrabalho.
- Se no futuro for necessário mais de um consumidor do mesmo evento, o port precisará evoluir para um EventEmitter completo — decisão conscientemente adiada (YAGNI).
- Também nesta revisão: `WhatsAppSession` (Domain) passou a incluir `tenantId`; `WhatsAppSessionRepository` ganhou `findByTenantAndSessionName`; `SessionManager.init()` passou a reaproveitar/atualizar sessão existente em vez de duplicar; `getStatus()` passou a lançar `WhatsAppSessionNotFoundError` (erro de Domain) em vez de `Error` genérico.

## 13. 2026-07-06 – Logger port compartilhado (M1A.1 — Architecture Hardening)
**Status**: Accepted
**Context**: O Architecture Review pré-Baileys (P7) encontrou zero observabilidade em todo o módulo WhatsApp. `CLAUDE.md` já define Winston como a biblioteca-alvo de logging, e uma implementação de referência (não-portável, sem interface) já existe na árvore legada `src/infrastructure/logger.ts`. Logging é uma preocupação transversal (cross-cutting), usada potencialmente por todos os bounded contexts da API (WhatsApp, IA, CRM, Analytics, Scheduler/BullMQ) — não é lógica de negócio (não é Domain Service) nem modelo de domínio compartilhado (não é Shared Kernel no sentido estrito de DDD).
**Decisão**: Criar o port `Logger` em `apps/api/src/shared/domain/Logger.ts` — nova convenção de pasta `shared/` dentro de `apps/api` para ports/utilitários reaproveitáveis entre bounded contexts, seguindo a mesma regra já usada por `WhatsAppProvider`/`WhatsAppSessionRepository` (a interface vive no Domain; a Infrastructure implementa). Contrato: `debug/info/warn/error(message, meta?)` + `child(bindings)` para logger vinculado a contexto (ex.: `tenantId`, `sessionName`) sem repetição manual. Duas implementações em `apps/api/src/shared/infrastructure/logging/`: `ConsoleLogger` (saída JSON estruturada em stdout/stderr, serializa `Error` corretamente) e `NoopLogger` (Null Object, permite que `Logger` seja dependência **obrigatória** nos construtores, sem parâmetros opcionais nem checagens de nulidade). `SessionManager` passa a receber `Logger` como terceiro parâmetro obrigatório do construtor.
**Consequências**:
- Nenhuma dependência de Winston (ou qualquer lib de log) vaza para Domain/Application — `ConsoleLogger` é descartável, trocável por `WinstonLogger` no futuro sem tocar o port ou os consumidores.
- `child()` incluído desde já para evitar retrabalho quando Baileys (Item 3) e BullMQ (Item 6) precisarem de contexto vinculado (`tenantId`, `sessionName`, `jobId`).
- Escopo deliberadamente restrito a logging — métricas e tracing (OpenTelemetry/Prometheus, ver `ARCHITECTURE.md` §9) ficam de fora deste port (ISP), e devem ganhar ports próprios no futuro.
- `SessionManager.init()` ainda não usa `child()` para vincular `tenantId`/`sessionName` ao logger no construtor — isso só faz sentido a partir de M1A.4, quando `SessionManager` passar a ser vinculado a uma única sessão. Por ora, esses campos são passados manualmente em cada chamada de log. Retrabalho pequeno e esperado, não um defeito.

## 14. 2026-07-06 – Canal de eventos genérico no port `WhatsAppProvider` (achado F2, Architecture Gate Review)
**Status**: Accepted
**Context**: Um Architecture Gate Review, simulando produção em escala (milhares de empresas, anos de operação), encontrou uma falha de Open/Closed no port `WhatsAppProvider`: `onStatusChange`/`WhatsAppProviderStatusUpdate` (ADR #12) só suportava um tipo de evento (mudança de status). QR Code, mensagens recebidas, presence e typing — todos exigidos pelo roadmap (Conversations, IA, Analytics) — exigiriam, cada um, um novo método no port e em toda implementação de `WhatsAppProvider`, uma mudança na interface a cada nova capacidade em vez de uma extensão aditiva.
**Decisão**: Substituir `onStatusChange` por `onEvent(listener: (event: WhatsAppProviderEvent) => void): void`, onde `WhatsAppProviderEvent` (`apps/api/src/services/whatsapp/domain/providers/WhatsAppProviderEvent.ts`) é uma união discriminada por `type`. Hoje só existe o membro `'status_changed'` (mesma forma de `WhatsAppProviderStatusUpdate`, migrada). `SessionManager.subscribeToProviderEvents` ignora (early return) qualquer tipo de evento que não reconheça, em vez de dar erro — permitindo que novos tipos sejam adicionados à união no futuro sem quebrar consumidores existentes.
**Consequências**:
- Novos tipos de evento (`qr_updated`, `message_received`, `presence_updated`, `typing_updated`) tornam-se apenas novos membros da união, quando o Item 3 (BaileysProvider) revelar a forma real de seus payloads — decisão deliberada de não antecipar esses formatos agora (evita abstração especulativa antes de uma necessidade real).
- `WhatsAppProviderStatusUpdate.ts` foi esvaziado e marcado como `@deprecated`, mantido apenas como referência para quem procurar o nome antigo (sem tooling de exclusão de arquivo disponível nesta sessão).
- ADR #12 marcada como superseded por esta.

## 15. 2026-07-06 – `provider` como enum (achado F6, Architecture Gate Review)
**Status**: Accepted
**Context**: O mesmo Gate Review encontrou `WhatsAppSession.provider`/coluna `provider` do Prisma como `String` livre, com valor `'baileys'` hardcoded na Application — mesma classe de bug já encontrada no schema legado (`ConversationStatus.CLOSED` referenciado em código, mas inexistente no enum real). Em escala (múltiplas centenas de empresas), uma string solta permite divergências silenciosas (`'Baileys'` vs `'baileys'`) sem nenhuma checagem em tempo de compilação ou de banco.
**Decisão**: Novo enum `WhatsAppProviderType` no Prisma (hoje só `BAILEYS`) e o campo `WhatsAppSession.provider` (Domain, TS) tipado como literal `'baileys'` em vez de `string`. Novos valores só são adicionados quando uma segunda implementação real de `WhatsAppProvider` existir (mesma disciplina de YAGNI aplicada ao achado F9).
**Consequências**:
- O literal `'baileys'` já existente em `SessionManager.ts` agora é checado pelo compilador contra o tipo da entidade — reduz (mas não elimina arquiteturalmente) o risco original do achado P5/F6: `SessionManager` (Application) ainda referencia textualmente um valor de Infrastructure (`'baileys'`), só que agora com segurança de tipo. A remoção completa dessa referência direta (ex.: via `provider.name` injetado) não fazia parte do escopo aprovado desta rodada e continua como melhoria possível, não classificada como bloqueante.
- `@@index([tenantId])` em `WhatsAppSession` pode ser redundante frente a `@@unique([tenantId, sessionName])` (que já serve como índice utilizável por prefixo esquerdo em `tenantId` sozinho) — identificado durante esta validação, não corrigido nesta rodada (fora do escopo aprovado de F2/F6/validação; ver relatório da revisão).

## 16. 2026-07-06 – Coordenação distribuída entre pods (achado F1) — adiada
**Status**: Deferred (documentada, não implementada)
**Context**: Em escala (10 pods Kubernetes, 100 mil sessões), o `WhatsAppConnectionRegistry` planejado (M1A.4, nunca implementado) resolveria concorrência apenas dentro de um processo — nada impede hoje que dois pods abram, simultaneamente, duas conexões Baileys para o mesmo número de WhatsApp.
**Decisão**: Não implementar agora. Quando o projeto migrar para deploy multi-pod real, será necessário um mecanismo de posse distribuída (lease) — coluna `lockedBy`/`leaseExpiresAt` no Postgres, ou lock no Redis com renovação periódica — consultado antes de qualquer tentativa de conexão. Também será necessário endereçar o roteamento de comandos do BullMQ e o fan-out de eventos para WebSocket entre pods (mesma causa raiz).
**Consequências**: Bloqueia deploy multi-pod/produção real, mas não bloqueia a implementação do `BaileysProvider` (Item 3) em instância única. Recomenda-se uma sub-milestone própria ("Distributed Coordination") antes de qualquer plano de escalar horizontalmente.
**Nota (2026-07-09)**: a ADR #54 (Milestone 3) resolveu o caso concreto de posse de socket entre `apps/api` e o novo `apps/worker` (BullMQ) sem antecipar esta ADR — via fila de comandos outbound (`whatsapp-outbound`) consumida exclusivamente dentro do processo `apps/api`, único dono dos sockets. As duas decisões são complementares, não conflitantes: quando esta ADR #16 for implementada de fato (múltiplas réplicas de `apps/api`), o mecanismo de lease se encaixa **atrás** do mesmo consumidor de `whatsapp-outbound` já introduzido pela ADR #54, sem exigir nenhuma mudança em `apps/worker` nem nos bounded contexts `ai`/`conversations`. Esta ADR permanece Deferred.

## 19. 2026-07-06 – Separação entre `WhatsAppChannel` e sessão de conexão (achado F5) — adiada
**Status**: Deferred (documentada, não implementada)
**Context**: `WhatsAppSession` conflaciona duas noções distintas: a identidade durável do canal (número, tenant, provider — muda raramente) e o estado efêmero de conexão (status, QR, última atividade — muda com frequência). Isso não causa problema hoje, mas não há onde pendurar regras de limite de plano por tenant (ex.: "máximo de 3 números por plano") sem acoplar com o registro de conexão volátil.
**Decisão**: Não implementar agora. Quando limites de plano/SaaS entrarem no roadmap, avaliar dois agregados separados — `WhatsAppChannel` (identidade) e a sessão de conexão referenciando o canal por ID — em vez de um agregado só, dado que write-frequency e consistency boundary de cada um são muito diferentes.
**Consequências**: Não bloqueia o Item 3; quanto mais tarde essa separação for feita, mais cara fica (exigiria migração de dados reais).

## 20. 2026-07-06 – Abstração para WhatsApp Cloud API/Meta Business API (achado F9) — adiada
**Status**: Deferred (documentada, não implementada)
**Context**: O port `WhatsAppProvider` modela implicitamente um provider orientado a socket (`connect()`/`disconnect()`/eventos de conexão) — adequado para Baileys/Evolution API/Green API, mas não para a Cloud API oficial da Meta, que não tem socket algum (autenticação por token, mensagens via webhook, sem "conectar"/"desconectar" no mesmo sentido).
**Decisão**: Não generalizar o port agora. Abstrair para cobrir ambos os modelos sem uma segunda implementação real para validar a forma certa seria abstração especulativa (regra das três instâncias). Registrar formalmente que `WhatsAppProvider`, no formato atual, é conhecidamente Baileys/socket-shaped e não deve ser assumido como pronto para a Cloud API.
**Consequências**: Se/quando a Cloud API se tornar um requisito real, esperar que este port seja dividido (ex.: `WhatsAppConnectionProvider` para os orientados a socket vs. uma forma distinta para os orientados a webhook), possivelmente unificados só numa abstração de "canal" de nível mais alto. Não bloqueia o Item 3.

## 21. 2026-07-06 – Persistência de credenciais: port genérico `CredentialsStore` + `Cipher` (antigo P2/M1A.6)
**Status**: Accepted, implementado
**Context**: A persistência do authState/credenciais do Baileys (P2 do primeiro Architecture Review, classificado "Crítica"/obrigatório antes do Baileys) nunca havia sido implementada e, por uma falha de processo, ficou de fora tanto da lista "implementar antes do Baileys" quanto da lista "adiar via ADR" do Architecture Gate Review (ADRs #14–#20). Achado durante a revisão final rápida pós-F2/F6; o usuário aprovou resolver antes do Item 3, mediante uma revisão arquitetural dedicada da solução proposta antes de qualquer código.
**Decisão**:
1. Não modelar o port em torno do formato interno do Baileys (que não é um blob único, e sim um key-value store do protocolo Signal com leitura/escrita por chave individual — dezenas a centenas de entradas por sessão). Fazer isso vazaria um detalhe de biblioteca concreta para o Domain, repetindo o erro já evitado no achado F9.
2. Port genérico `CredentialsStore` (`get`/`getAll`/`set`/`remove`/`clear`, endereçado por `tenantId` + `namespace` + `key`), sem nenhum conceito de WhatsApp — reutilizável por qualquer futuro consumidor que precise guardar segredos por tenant.
3. Port separado `Cipher` (`encrypt`/`decrypt`, recebendo `tenantId`) para SRP: o store cuida de onde o dado mora, o cipher cuida de como é protegido.
4. Ambos vivem em `apps/api/src/shared/security/domain/` — não em `services/whatsapp/domain/` (mesmo racional já usado para o `Logger`, que vive em `shared/domain/`) — mas num subnamespace `security/` próprio, distinto de `shared/domain/` genérico, para que código que lida com segredos tenha um local claramente identificável para auditorias.
5. Implementações concretas em `shared/security/infrastructure/`: `AesGcmCipher` (AES-256-GCM, chave derivada por tenant via HKDF a partir de uma chave mestra — evita uma única chave global cujo vazamento comprometeria todos os tenants de uma vez) e `PrismaCredentialsStore` (model `TenantCredential`, sem FK para `WhatsAppSession` — só para `Tenant` — para desacoplar o ciclo de vida do segredo do registro operacional de sessão).
6. Encriptação em nível de aplicação, não `pgcrypto` (desvio deliberado, documentado, da ADR #6 original — mesma razão de portabilidade/testabilidade já usada para o Logger e para o restante deste módulo).
**Consequências**:
- Trade-off aceito: chaves derivadas de uma única chave mestra via HKDF significam que rotacionar a chave mestra invalida todas as chaves de uma vez — sem isolamento de rotação por tenant. Resolver com KMS real por tenant é melhoria futura que só troca a implementação de `Cipher`, nunca o port.
- Trade-off aceito: Postgres para armazenar um key-value de escrita potencialmente frequente (chaves Signal mudam a cada troca de mensagem) é aceitável para o volume atual; se o throughput de escrita virar gargalo medido em produção, uma implementação Redis-backed substitui `PrismaCredentialsStore` sem mudar o port.
- Não bloqueia o Item 3: `BaileysProvider` poderá receber `CredentialsStore` diretamente no construtor (sem depender de um `ProviderFactory`, que segue adiado — achado F1) e usá-lo internamente para adaptar o formato esperado pelo `SignalKeyStore` do Baileys, mantendo esse detalhe inteiramente na Infrastructure.
- `PrismaCredentialsStore` referencia `prisma.tenantCredential`, dependente de `npx prisma generate` — não executável neste sandbox (mesma limitação já registrada para o restante do schema desta Milestone); precisa ser conferido com `tsc`/`prisma generate` no ambiente real antes do primeiro uso em produção.

## 22. 2026-07-06 – `BaileysProvider` (Milestone 1, Item 3): pacote, mapeamento de status e adapter de credenciais
**Status**: Accepted, implementado

## 23. 2026-07-06 – Correção de BUG-01 a BUG-04 (auditoria adversarial independente)

**Status**: Accepted, implementado
**Context**: Auditoria técnica independente (Principal Software Architect / Code Reviewer externo, papel deliberadamente adversarial) sobre toda a Milestone 1 (Item 1, M1A, Item 3) encontrou 4 bugs reais de ciclo de vida/concorrência em código já implementado, além de 7 achados de gravidade menor. A auditoria concluiu "existe retrabalho obrigatório antes do Item 4". Esta ADR registra a correção dos 4 bugs críticos/altos; os achados de gravidade menor (BUG-05 a BUG-11: `CredentialsStore.getAll()` sem chamador real, falta de evento `qr_updated`, erro genérico em `getQRCode()`, organização de `shared/`, falta de versionamento de chave, `as never` em testes, cobertura de teste só do caminho feliz) permanecem registrados, não corrigidos nesta rodada — fora do escopo explicitamente pedido.

**Decisão / correções:**

1. **BUG-01 (Crítica) — Race condition, eventos perdidos**: `SessionManager.init()` chamava `provider.onEvent(listener)` DEPOIS de `provider.connect()`. Qualquer evento emitido pelo provider nessa janela (comum: o primeiro QR, ou reconexão quase instantânea para `'connected'` com credenciais em cache) era descartado silenciosamente (`this.eventListener?.(...)` no provider não fazia nada sem listener registrado). Corrigido invertendo a ordem: assina eventos ANTES de conectar, e persiste um registro inicial (`'connecting'`) antes disso, garantindo que o handler assíncrono sempre encontre uma linha existente para atualizar.

2. **BUG-02 (Crítica) — Reconexão pós-restart nunca acontecia**: o "early return" de `init()` confiava cegamente em `existing.status === 'connected'` persistido no banco. Depois de um restart do servidor, uma sessão marcada `'connected'` antes do crash fazia `init()` retornar sem NUNCA chamar `provider.connect()` — a persistência de credenciais (M1A.6) não cumpria sua própria razão de existir. Corrigido: a única fonte de verdade sobre "existe conexão viva NESTE processo" passa a ser `provider.getStatus()` (que um provider recém-criado sempre reporta honestamente como não conectado), nunca o banco isoladamente. O early-return agora também cobre `'connecting'` (evita reconectar redundantemente em cima do próprio BUG-04).

3. **BUG-03 (Alta) — API pública enganosa, sem checagem de posse**: `disconnect(sessionId)`/`getStatus(sessionId)` aceitavam qualquer `sessionId`, mas só existe UM `provider` por instância de `SessionManager`. Chamar com o `sessionId` de outra sessão desconectava/lia o provider errado e gravava o resultado na linha errada do banco, silenciosamente. Corrigido com um campo `ownedSessionId` (atribuído no primeiro `init()` bem-sucedido) e `assertOwnsSession()`, que lança o novo erro de Domain `WhatsAppSessionOwnershipError` quando o `sessionId` não corresponde à sessão gerenciada por esta instância.

4. **BUG-04 (Alta) — Socket zumbi em reconexões múltiplas**: `BaileysProvider.connect()` assumia ser chamado uma única vez por instância. Chamadas repetidas (reconexões normais) criavam um socket novo sem nunca encerrar o anterior (vazamento de timers/handles do Baileys), e o socket antigo podia disparar um evento tardio que sobrescrevia o estado do socket novo ("status flapping"). Corrigido com `teardownSocket()` (chamado no início de `connect()` e em `disconnect()`) e um check de identidade dentro do handler de `connection.update` (`this.socket !== socket`, onde `socket` é a variável local capturada por closure na chamada de `connect()` que registrou aquele handler) que ignora eventos de um socket já substituído.

**Consequências:**
- Nenhuma mudança de contrato público (assinaturas de `WhatsAppProvider`/`SessionManager` inalteradas, exceto o novo erro que `disconnect`/`getStatus` podem lançar — mudança aditiva).
- `SessionManager.test.ts` e `BaileysProvider.test.ts` ganharam testes dedicados a cada bug, incluindo um Fake de provider corrigido (`FakeWhatsAppProvider.status` agora inicia `'disconnected'`, não `'connected'` — o Fake anterior mascarava o BUG-02 ao "mentir" que já estava sempre conectado por padrão) e um mock de socket que cria objetos distintos por chamada (necessário para provar o teardown/identity-check do BUG-04).
- BUG-05 a BUG-11 (gravidade Média/Baixa da mesma auditoria) permanecem registrados e não corrigidos — não fazem parte desta ADR.

## 25. 2026-07-06 – Correção do P6: `upsertByTenantAndSessionName` (revisão arquitetural Item 4 + integração Item 3↔4)

**Status**: Accepted, implementado
**Context**: Revisão arquitetural dedicada ao Item 4 e à integração Item 3↔4 (pedida explicitamente antes do Item 5) encontrou que o P6 (race condition de `init()` concorrente, conhecido desde a Architecture Review original e nunca corrigido) tinha se tornado **concretamente alcançável** com um `PrismaWhatsAppSessionRepository` real: duas chamadas de `init()` para a mesma `tenantId`+`sessionName` colidem na constraint `@@unique`, e a `create()` da chamada perdedora lança uma exceção não tratada. Agravante: o `FakeWhatsAppSessionRepository` usado em todos os testes de `SessionManager` não impõe essa mesma invariante — os testes nunca poderiam detectar essa falha, dando falsa confiança (o mesmo padrão de "Fake mais tolerante que a implementação real" que já havia causado o BUG-02).
**Decisão**: adicionar `upsertByTenantAndSessionName(tenantId, sessionName, create, update)` ao port `WhatsAppSessionRepository` — uma operação atômica no nível do banco (implementação Prisma usa `upsert()`, que compila para `INSERT ... ON CONFLICT (tenant_id, session_name) DO UPDATE` no Postgres). `SessionManager.init()` foi refatorado para usar essa operação em vez do antigo `find` seguido de `create()`/`update()` separados — fechando inteiramente a janela de corrida (TOCTOU) entre a leitura e a escrita. O `id` definitivo da sessão passa a ser sempre o valor de RETORNO do upsert, nunca o `id` especulativo gerado localmente antes da chamada — se outra chamada concorrente já tiver vencido a corrida no banco, esta chamada converge para a MESMA linha, sem duplicar e sem lançar.
**Consequências**:
- `FakeWhatsAppSessionRepository` (testes) implementa a mesma operação, com um helper de teste (`forcedUpsertResult`) que simula explicitamente o cenário de corrida vencida por outra chamada — prova que `SessionManager` usa o `id` do retorno, não o especulativo.
- Nenhuma mudança de contrato quebra consumidores existentes de `WhatsAppSessionRepository` — `upsertByTenantAndSessionName` é um método NOVO, aditivo.
- `create()`/`update()` continuam existindo no port (usadas por outras operações, ex.: a atualização final pós-`connect()` e o handler de eventos assíncronos) — não foram removidas.
- Achados de gravidade Média/Baixa da mesma revisão (`findAll()` sem escopo de tenant/paginação, sem chamador real; divergência teórica Fake↔Real em `update()` com valor `undefined` explícito) foram registrados mas **não corrigidos** — não bloqueiam o Item 5.

## 26. 2026-07-06 – Auditoria de integração (Item 3↔4, cadeia completa) — BUG-12 e BUG-13 corrigidos

**Status**: Accepted, implementado
**Context**: Auditoria de integração (não conceitual) simulando o ciclo de vida completo (primeira conexão, QR, pareamento, credenciais atualizando, restart, reconexão, desconexão, logout, troca de QR, concorrência, falha de banco) através de toda a cadeia `SessionManager → BaileysProvider → CredentialsAdapter → CredentialsStore → Cipher → Prisma → Banco`. Encontrou 10 achados (BUG-12 a BUG-21); 2 de gravidade Alta, corrigidos nesta ADR.
**Decisão**:
1. **BUG-12** — o handler de `creds.update` em `BaileysProvider.connect()` não tinha o mesmo check de identidade (`this.socket !== socket`) já aplicado ao handler de `connection.update` (BUG-04, ADR #23). Um `creds.update` tardio de um socket já substituído/encerrado (reconexão) podia sobrescrever a chave `'creds'` no banco com dados desatualizados. Corrigido aplicando o mesmo check de identidade, e adicionado tratamento de erro (`saveCreds().catch(...)` com log) que também estava ausente — mesma classe de risco de unhandled rejection que motivou o Logger em M1A.1.
2. **BUG-13** — nenhuma limpeza de credenciais ao detectar `DisconnectReason.loggedOut` (logout real do usuário pelo celular). Credenciais persistidas ficavam inválidas mas continuavam armazenadas, sendo recarregadas numa tentativa futura de reconexão em vez de um QR novo ser gerado. Corrigido chamando `credentialsStore.clear(tenantId, namespace)` quando `loggedOut === true`, dentro do próprio `BaileysProvider` (já tem acesso a `credentialsStore` via construtor — não precisa de participação da Application).
**Consequências**:
- Nenhuma mudança de contrato público — ambas as correções são internas a `BaileysProvider`.
- Testes novos em `BaileysProvider.test.ts` (`describe('BUG-12 ...')`, `describe('BUG-13 ...')`) provam: evento de socket obsoleto não persiste; socket atual continua persistindo normalmente; falhas em ambas as operações são logadas, não lançam.
- **Achados registrados, não corrigidos nesta rodada (Média/Baixa)**: BUG-14 (`latestQrCode` nunca limpo — pode devolver QR expirado/irrelevante após conectar ou reconectar com credenciais em cache), BUG-15 (reconfirmação do BUG-06: sem evento `qr_updated`, troca de QR só via polling), BUG-16 (sem coordenação/transação entre a escrita de `WhatsAppSession.status` e `TenantCredential` — tabelas diferentes; crash exatamente entre os dois eventos pode deixar o banco "conectado" com credenciais ainda não salvas), BUG-17 (`keys.set()` do adapter usa `Promise.all` sem atomicidade — falha parcial pode persistir algumas chaves do Signal e perder outras da mesma chamada), BUG-18 (sem retry na persistência assíncrona de eventos — mitigado parcialmente porque `getStatus()` sempre prioriza o status ao vivo do provider), BUG-19 (port ainda expõe `create()` "inseguro" ao lado do `upsertByTenantAndSessionName()` atômico — nada impede reintrodução do P6 por um consumidor futuro), BUG-20 (exceções do Prisma podem propagar até a Application sem tradução para erro de Domain), BUG-21 (gaps de teste: mock de socket popula `.user` desde a criação, não só após `'open'`; nenhum teste cobria `creds.update`/`loggedOut`/`getQRCode()` pós-reconexão antes desta ADR — exatamente por isso BUG-12/13 passaram despercebidos em duas auditorias anteriores).

## 32. 2026-07-08 – BUG-14: reconexão automática obrigatória após `restartRequired` (515)
**Status**: Superseded pela ADR #47 (Production Hardening, Bloco 8b) — a reconexão automática deixou de ser um `if (restartRequired)` hard-coded e incondicional, e passou a ser delegada a uma `ReconnectionPolicy` (backoff exponencial + circuit breaker) para QUALQUER motivo recuperável, não só `restartRequired`. Mantido aqui como registro histórico do problema original e da correção inicial; a frase "nenhum outro motivo de desconexão passou a reconectar automaticamente", abaixo, **não reflete mais o código atual** — ver ADR #47.
**Contexto**: Teste manual real com WhatsApp: o pareamento (QR) era aceito pelo WhatsApp (log do Baileys: `"pairing configured successfully, expect to restart the connection..."`), mas o celular sempre reportava "não foi possível conectar dispositivo". Causa raiz: o protocolo WhatsApp Multi-Device exige encerrar e reabrir a conexão UMA vez logo após o pareamento, sinalizado por `connection.update` com `statusCode 515` (`DisconnectReason.restartRequired`). `BaileysProvider` tratava isso como qualquer outra desconexão — nunca reconectava — então a segunda metade do handshake nunca acontecia e o vínculo nunca se completava do lado do WhatsApp, mesmo com credenciais válidas já salvas.
**Decisão (histórica, superseded)**: `handleConnectionUpdate` chama `this.connect()` automaticamente quando detecta `statusCode === DisconnectReason.restartRequired`. Nenhum outro motivo de desconexão passou a reconectar automaticamente (mantido o comportamento anterior). Mesmo padrão recomendado pela documentação/exemplos oficiais do Baileys.
**Impacto**: Confirmado por teste manual real após o fix: pareamento completo com número real (`5521982925941`), dispositivo "Ubuntu Chrome" listado em Aparelhos Conectados no celular. Fluxo POST → QR → Scan → Connected → Status → Disconnect validado de ponta a ponta. Adiciona 2 testes de regressão em `BaileysProvider.test.ts` (BUG-14).

## 33. 2026-07-07 – `WhatsAppSessionKey` (Item 5, Bloco 1): Value Object de identidade de sessão

**Status**: Accepted, implementado
**Context**: O futuro `WhatsAppConnectionRegistry` (Bloco 5) precisa de uma chave canônica de `Map` para reaproveitar instâncias por `(tenantId, sessionName)` — a mesma dupla de `@@unique([tenantId, sessionName])`. Concatenar strings ad-hoc no código chamador repetiria essa lógica em múltiplos lugares e arriscaria colisão entre chaves logicamente diferentes (ex.: `tenantId="a:b"` + `sessionName="c"` vs. `tenantId="a"` + `sessionName="b:c"`, se o separador fosse algo comum como `:`). Item parcialmente coberto pela ADR #18 (achado F4, `SessionKey` adiado) — este bloco implementa a parte de chave composta (não o `PhoneNumber` VO, que continua fora de escopo).
**Decisão**: `WhatsAppSessionKey` (`domain/valueObjects/WhatsAppSessionKey.ts`) — Value Object imutável (`Object.freeze`), sem dependência de Infrastructure. `toString()` usa o caractere NUL (`String.fromCharCode(0)`) como separador canônico — praticamente impossível de aparecer em `tenantId` (UUID) ou `sessionName` (nome legível), e o construtor rejeita explicitamente qualquer parte que contenha esse caractere, fechando a janela de colisão por completo. `equals()` compara por valor, nunca por referência.
**Consequências**:
- `SessionManager` (ADR #29) passa a receber esta instância no construtor, em vez de `tenantId`/`sessionName` soltos.
- `toString()` é deliberadamente só para uso interno como chave de `Map` — nunca deve ser exibido ao usuário nem persistido.

## 36. 2026-07-07 – `WhatsAppConnectionRegistry` (Item 5, Bloco 5): pool de `SessionManager` por sessão

**Status**: Accepted, implementado
**Context**: Sem um pool, cada requisição HTTP (Bloco 7) criaria um `SessionManager`/`WhatsAppProvider` novo, perdendo qualquer conexão em andamento a cada chamada — inviabilizando o próprio propósito de uma sessão persistente de WhatsApp.
**Decisão**: `WhatsAppConnectionRegistry` (Application) mantém um `Map<string, SessionManager>` chaveado pelo `toString()` de `WhatsAppSessionKey` (ADR #33). `getOrCreate(tenantId, sessionName)` cria a instância (e o `provider` correspondente, via `WhatsAppProviderFactory`, ADR #34) na primeira chamada para aquele par, e devolve a MESMA instância em qualquer chamada seguinte. **Consequências**:
- `evictIfCurrent(tenantId, sessionName, expectedGeneration)` foi adicionado depois (Production Hardening, Bloco 4 — ver ADR #42) para permitir remoção segura de entradas sem orfanar conexões reconectadas concorrentemente.
- Nenhum limite de tamanho de `Map`/TTL de entradas inativas implementado nesta milestone — sessões desconectadas continuam ocupando uma entrada até o processo reiniciar. Risco de memória de baixa prioridade, não bloqueante no volume atual, candidato a revisão futura junto da coordenação distribuída (ADR #16).

## 40. 2026-07-08 – Production Hardening, Bloco 2: `ApiKeyHasher` — HMAC-SHA256 com pepper

**Status**: Accepted, implementado
**Context**: Autenticação por `X-API-Key` (Bloco 6) exige armazenar um hash da chave, nunca a chave em texto plano, e verificar apresentações futuras contra esse hash. Revisão arquitetural (mesma rodada da ADR #39) avaliou bcrypt/Argon2/scrypt vs. HMAC.
**Decisão**: `ApiKeyHasher` (port, `shared/security/domain/`) com `hash()`/`verify()` — deliberadamente unidirecional (sem `decrypt`), diferente de `Cipher` (ADR #21), que é reversível. `HmacSha256ApiKeyHasher` (Infrastructure) implementa via HMAC-SHA256 com pepper, não bcrypt/Argon2: (1) API keys são geradas aleatoriamente (alta entropia) — hash lento/memory-hard não compra segurança adicional aqui, só paga latência; (2) bcrypt/Argon2 são não-determinísticos (salt aleatório embutido), incompatível com `TenantRepository.findByApiKeyHash(hash)` (ADR #39), que depende de igualdade direta contra uma coluna `@unique` indexada — com hash não-determinístico seria necessário buscar TODOS os tenants e comparar um a um, perdendo o lookup O(1). `verify()` usa `crypto.timingSafeEqual` (nunca `===` direto) para evitar timing attack.
**Consequências**:
- O pepper é recebido via construtor (nunca lido de `process.env` diretamente pela classe) — mesma separação já usada em `AesGcmCipher`.
- Trade-off aceito: o pepper é um único segredo global (não derivado por tenant, ao contrário da chave de `AesGcmCipher`) — API keys não têm o mesmo "blast radius" de credenciais de sessão do WhatsApp (revogar/reemitir uma API key é uma operação O(1) e sem efeito colateral em outros tenants).

## 42. 2026-07-08 – Production Hardening, Bloco 4: contador de `generation` + `evictIfCurrent` (evicção segura do Registry)

**Status**: Accepted, implementado
**Context**: Revisão arquitetural dedicada (cinco rodadas de auditoria adversarial) encontrou uma race condition estrutural entre `WhatsAppSessionService.disconnectSession()` (que precisa remover a entrada do `WhatsAppConnectionRegistry` depois de desconectar, para não vazar memória) e uma reconexão concorrente da MESMA sessão — via nova chamada HTTP de `init()` OU via a reconexão automática interna do `BaileysProvider` (então só para `restartRequired`/515, ADR #32; hoje generalizada, ADR #47). Remover incondicionalmente do `Map` depois de um `disconnect()` corria o risco de orfanar uma conexão reconectada nesse meio-tempo — a próxima `getOrCreate()` criaria uma instância NOVA, e a antiga (já reconectada) ficaria invisível ao Registry para sempre.
**Decisão**: `SessionManager` ganha um campo privado `generation` (contador, começa em 0), incrementado APENAS dentro de `subscribeToProviderEvents()` quando `event.status === 'connecting'` (nunca em leituras puras como `getStatus()`/`getQRCode()`, o que reabriria o problema ao impedir evicções legítimas sob polling frequente). `getGeneration()` expõe o valor atual (leitura pura, síncrona). `WhatsAppConnectionRegistry.evictIfCurrent(tenantId, sessionName, expectedGeneration)` só remove a entrada do `Map` se a geração atual da instância ainda for igual a `expectedGeneration` — captura-se a geração ANTES de chamar `disconnect()`, e a comparação só remove se ninguém reconectou nesse intervalo. Tanto o incremento quanto a comparação são inteiramente síncronos — a garantia de single-thread do event loop do Node torna as duas seções críticas impossíveis de se intercalar.
**Consequências**:
- `WhatsAppSessionService.disconnectSession()` (ADR #43) é o único consumidor real deste mecanismo: captura `sessionManager.getGeneration()` antes de `disconnect()`, chama `evictIfCurrent()` depois.
- O campo `generation` vive na instância (`this.generation`), nunca numa variável local capturada por closure — a closure de `subscribeToProviderEvents()` é recriada a cada reconexão real, então uma variável local seria reiniciada a cada reconexão, anulando o mecanismo silenciosamente.
- Nenhum limite de tamanho ou TTL para entradas do `Map` foi adicionado neste bloco (mesmo risco de baixa prioridade já registrado na ADR #36).

## 44. 2026-07-08 – Production Hardening, Bloco 6: `requireApiKey` + `resolveTenantFromApiKey` + `sanitizeHeaders` (fecha o IDOR/C1)

**Status**: Accepted, implementado
**Context**: Sem autenticação HTTP, qualquer chamador poderia operar sobre sessões de QUALQUER tenant só sabendo o `tenantId` na URL — um IDOR (Insecure Direct Object Reference, achado C1 desta revisão). Era necessário tanto autenticação (quem é o dono desta API key?) quanto autorização (esse tenant pode agir sobre ESTE recurso específico da URL?).
**Decisão**:
1. `resolveTenantFromApiKey` (`shared/tenant/application/`) — função PURA (não uma classe, ao contrário de `WhatsAppSessionService`, ADR #43, por ter uma única responsabilidade minúscula): hasheia a API key recebida (`ApiKeyHasher.hash()`, ADR #40) e busca o tenant dono via `TenantRepository.findByApiKeyHash()` (ADR #39). Retorna `null` para chave ausente/inválida — nunca lança.
2. `createRequireApiKey` (`services/whatsapp/presentation/requireApiKey.ts`) — middleware Express de 4 passos: (a) extrai `X-API-Key` (ausente → 401 `missing_api_key`); (b) resolve o tenant via `resolveTenantFromApiKey` (inválida → 401 `invalid_api_key`); (c) SE a rota tiver `:tenantId` no path, compara com o tenant autenticado (divergência → 403 `tenant_mismatch` — este é o passo que fecha o IDOR/C1); (d) anexa `req.tenant` e chama `next()`. Header customizado `X-API-Key` (não `Authorization: Bearer`) — decisão fechada nesta revisão.
3. `sanitizeHeaders` (`shared/infrastructure/logging/`) — nunca loga `x-api-key`/`authorization`/`cookie`/`set-cookie` crus, em nenhuma circunstância (comparação case-insensitive). Usado em todo log de rejeição do middleware.
**Consequências**:
- Vive em `services/whatsapp/presentation/` (não em `shared/`) — único consumidor real hoje é o router de sessões do WhatsApp; extrair prematuramente repetiria o erro de abstração especulativa já rejeitado para `Tenant` (categoria `core/`).
- IDOR/C1 fechado e provado por teste de integração dedicado (`whatsAppSessionsIntegration.test.ts`, Bloco 7/ADR #45) que monta middleware + router juntos.

## 46. 2026-07-08 – Production Hardening, Bloco 8a: `disconnectReason` — classificação do motivo da última desconexão

**Status**: Accepted, implementado (resolve parcialmente o achado P4 da ADR #22/PROJECT_STATUS.md §8)
**Context**: `WhatsAppSession['status']` continua com só 3 valores (`connecting`/`connected`/`disconnected`, achado P4, deliberadamente não expandido — ver ADR #15/#22 para o mesmo racional de YAGNI já aplicado a `provider`). Isso não distingue "queda temporária recuperável" de "usuário deslogou, precisa QR novo" — informação necessária para decidir reconexão automática (Bloco 8b, ADR #47) e para uma futura UI mostrar diagnóstico útil ao usuário.
**Decisão**: Campo NOVO e SEPARADO `WhatsAppSession.disconnectReason?: WhatsAppDisconnectReason` (não uma expansão do enum `status`) — misturar ESTADO (do qual `generation`/Registry dependem estruturalmente) com MOTIVO (por que a última queda aconteceu) impediria representar "reconectando depois de um logout" sem perder o sinal de `'connecting'`. `WhatsAppDisconnectReason` = `'logged_out' | 'restart_required' | 'connection_lost' | 'timed_out' | 'unknown'` — subconjunto deliberadamente pequeno dos códigos do Baileys (YAGNI, mesmo racional do achado F6). `BaileysProvider.mapDisconnectReason()` traduz o `statusCode` numérico do Baileys para este tipo; limpo (`undefined`) ao entrar em `'connecting'`/`'connected'`.
**Descoberta técnica (verificada lendo `node_modules/@whiskeysockets/baileys/lib/Types/index.d.ts`, não suposta)**: `DisconnectReason.connectionLost` e `DisconnectReason.timedOut` são o MESMO valor numérico (408) na biblioteca real — `'timed_out'` permanece no tipo de Domain por completude/documentação, mas é estruturalmente INALCANÇÁVEL a partir de `BaileysProvider` hoje; 408 sempre mapeia para `'connection_lost'`.
**Persistência**: `prisma/schema.prisma` ganhou o enum `WhatsAppDisconnectReason` + coluna nullable `disconnect_reason` em `WhatsAppSession`. `PrismaWhatsAppSessionRepository.update()`/`upsertByTenantAndSessionName()` tratam este campo por PRESENÇA DE CHAVE (`'disconnectReason' in data`), não por valor — diferente do padrão `!== undefined` usado para os demais campos opcionais, porque aqui `undefined` é um valor válido e intencional ("motivo limpo"), não "sem informação nova". `SessionManager.subscribeToProviderEvents` inclui a chave incondicionalmente por esse motivo.
**Consequências**: Nenhuma mudança de contrato pública que quebre consumidores existentes — campo aditivo em `WhatsAppSession`/evento `status_changed`.

## 47. 2026-07-08 – Production Hardening, Bloco 8b: reconexão automática com backoff exponencial + circuit breaker (`ReconnectionPolicy`)

**Status**: Accepted, implementado — **supersede a ADR #32 (BUG-14)**
**Context**: Antes deste bloco, só `DisconnectReason.restartRequired` (515) reconectava automaticamente, de forma imediata e incondicional, hard-coded dentro de `BaileysProvider.handleConnectionUpdate` (ADR #32/BUG-14). Qualquer outra queda recuperável (`connection_lost`, `unknown`) exigia intervenção manual (nova chamada HTTP de `init()`). Com `disconnectReason` classificado (ADR #46), era possível generalizar a reconexão automática para todo motivo recuperável — mas uma reconexão imediata e ilimitada para QUALQUER queda arriscaria um loop infinito de tentativas contra um WhatsApp temporariamente indisponível.
**Decisão**:
1. `isDisconnectReasonRecoverable(reason): boolean` (Domain, `domain/policies/`, função pura sem estado/timers) — só `'logged_out'` é definitivo; todos os demais motivos são recuperáveis. Separada deliberadamente de "quando tentar" (não conhece backoff/circuit breaker).
2. Port `ReconnectionPolicy` (`domain/providers/`) com `scheduleReconnect(reason, onRetry)`, `reset()`, `cancelPending()`. Implementação `WhatsAppReconnectionPolicy` (Infrastructure): backoff exponencial `delay(n) = min(baseDelayMs * factor^(n-1), maxDelayMs)`; circuit breaker abre após `consecutiveFailures > maxConsecutiveFailures` (loga em `warn`) e para de agendar novas tentativas até `reset()`; `reset()` chamado por `BaileysProvider` só numa conexão bem-sucedida (`connection === 'open'`). Config default: `{ baseDelayMs: 1000, factor: 2, maxDelayMs: 30000, maxConsecutiveFailures: 5 }`.
3. `BaileysProvider` não conhece `setTimeout`/contadores — só delega ao `reconnectionPolicy` recebido no construtor (SRP: este arquivo continua falando apenas o protocolo Baileys). `connect()`/`disconnect()` chamam `cancelPending()` no início, para que uma ação explícita nunca conviva com um timer de retry obsoleto agendado por uma falha anterior.
4. `BaileysProviderFactory` cria uma NOVA `WhatsAppReconnectionPolicy` a cada `create()` — estado de backoff/circuito é por sessão, nunca compartilhado entre tenants (só a config, imutável, é compartilhada).
**Consequências**:
- Comportamento observável muda para `statusCode` que antes NUNCA reconectava (ex.: `500`/`unknown`) — agora também agenda reconexão via a política, mudança deliberada e coberta por testes novos (`BaileysProvider.test.ts`, describe reescrito).
- Risco conhecido, não corrigido nesta rodada: uma vez que o circuito abre, só uma conexão BEM-SUCEDIDA o fecha (`reset()`) — uma chamada explícita de reconexão via HTTP (`POST .../whatsapp-sessions`, que aciona `connect()` diretamente) só cancela o timer pendente (`cancelPending()`), mas NÃO reseta o contador de falhas/circuito. Se essa tentativa explícita também falhar, o `close` resultante chama `scheduleReconnect()` de novo, que encontra o circuito ainda aberto e não agenda nada — nenhuma tentativa automática subsequente ocorre até uma conexão bem-sucedida ou reinício do processo. Comportamento intencional (evita mascarar uma falha persistente com retries infinitos), mas vale documentar para quem for operar a API: uma sessão com circuito aberto pode exigir múltiplas chamadas manuais de reconexão.
- `latestQrCode` continua nunca sendo limpo (achado BUG-14 antigo da auditoria de integração — numeração de achado, não confundir com o BUG-14 da ADR #32 — registrado na ADR #26, ainda não corrigido).

## 29. 2026-07-07 – Refatoração do `SessionManager` (Item 5, Bloco 3): identidade via `WhatsAppSessionKey`, mutex de ciclo de vida, remoção de `assertOwnsSession`

**Status**: Accepted, implementado
**Context**: Revisão arquitetural independente do desenho do `SessionManager` antes do Item 5 (endpoints REST), que exige um `WhatsAppConnectionRegistry` reaproveitando instâncias de `SessionManager` por `(tenantId, sessionName)`. A revisão rejeitou uma proposta anterior (adicionar `getTenantId()`/`getSessionName()` ao port `WhatsAppProvider`) por ampliar desnecessariamente a interface pública do provider, e encontrou uma race condition nova (achado F3) não coberta pela proposta original de guarda de concorrência.

**Decisão**:
1. **Identidade única via `WhatsAppSessionKey`** (não duplicada, não adicionada ao port `WhatsAppProvider`): `SessionManager` passa a receber `WhatsAppSessionKey` (Bloco 1) no construtor — `constructor(provider, sessionKey, repo, logger)`. `init()`, `getStatus()`, `disconnect()` deixam de aceitar qualquer parâmetro de identidade externa (`tenantId`/`sessionName`/`sessionId`). O futuro `WhatsAppConnectionRegistry` (Bloco 5) cria UMA `WhatsAppSessionKey` e deriva dela tanto os argumentos de `WhatsAppProviderFactory.create(tenantId, sessionName)` quanto a instância passada ao construtor do `SessionManager` — nunca duas fontes de verdade separadas.
2. **Remoção de `WhatsAppSessionOwnershipError`/`assertOwnsSession`** (ADR #23, BUG-03): a proteção em runtime deixa de ser necessária porque não existe mais nenhum parâmetro de identidade externo para divergir do que a instância gerencia — o bug que ela mitigava se torna estruturalmente impossível, não apenas verificado. Arquivo `WhatsAppSessionOwnershipError.ts` fica órfão (sem consumidor) — este sandbox não tem capacidade de excluir arquivos; recomenda-se removê-lo manualmente (`Remove-Item apps/api/src/services/whatsapp/domain/errors/WhatsAppSessionOwnershipError.ts`).
3. **Mutex de ciclo de vida (`lifecycleLock`)**: serializa `init()` e `disconnect()` entre si (fila de promises encadeadas, sempre resolve mesmo se a operação anterior rejeitar). Corrige uma race NOVA encontrada na revisão (achado F3): sem essa serialização, um `disconnect()` chamado enquanto um `init()` está em andamento podia rodar o teardown do socket ANTES do socket novo ser criado por `connect()` — e `connect()` prosseguia e criava o socket DEPOIS do disconnect já ter "acontecido". `getStatus()`/`getQRCode()` ficam deliberadamente FORA do mutex (achado F5) — são leituras puras; incluí-las bloquearia consulta de status durante uma conexão em andamento, justo quando o cliente mais quer ver progresso.
4. **`disconnect()` idempotente**: se a sessão nunca foi resolvida (nem por `init()` nesta instância, nem encontrada no repositório), não lança — só não persiste nada. `getStatus()` continua lançando `WhatsAppSessionNotFoundError` no mesmo cenário (assimetria deliberada, mesma convenção de idempotência de DELETE vs. leitura de GET em APIs REST).
5. **Risco aceito e não resolvido (achado F4, deferred)**: não existe timeout em `provider.connect()`. Se `connect()` nunca resolver, um `disconnect()` enfileirado atrás dele no `lifecycleLock` fica bloqueado indefinidamente — sem jeito de forçar a desconexão de uma sessão travada via API a não ser reiniciando o processo. Decisão explícita de não implementar timeout nesta milestone (mesmo precedente do achado F1/ADR #16) — revisitar se acontecer na prática.

**Consequências**:
- Mudança de contrato público do `SessionManager` (construtor + assinatura dos 4 métodos públicos) — intencional e documentada. Nenhum consumidor externo ao módulo WhatsApp existe ainda (Registry/rotas são Blocos futuros), então não há quebra real hoje.
- `SessionManager.test.ts` inteiramente reescrito: testes `[BUG-03]` removidos (cenário não é mais possível); teste "isolar sessões por tenant" adaptado para usar duas instâncias separadas (o padrão antigo de variar identidade na mesma instância é exatamente o que a refatoração elimina); testes novos para o mutex (F3: `disconnect()` aguarda `init()` em andamento; F5: `getStatus()` não é bloqueado pelo mutex) e para dedução de conexão única sob `init()` concorrente.
- `WhatsAppProvider` (port) permanece INALTERADO — nenhuma das implementações (`BaileysProvider`, Fakes) precisou de qualquer método novo.
- Restrição permanente documentada no código: `init()`/`getStatus()`/`disconnect()` nunca devem voltar a aceitar um parâmetro de identidade externa — reintroduzir isso reabre o BUG-03 sem nenhum erro de compilação avisando.

## 50. 2026-07-09 – Milestone 2, Fase 3: BFF completo (Next.js como Backend-for-Frontend)

**Status**: Accepted, implementado
**Context**: Decisão de arquitetura pré-aprovada para a Milestone 2 (ver ADR #52): o Dashboard nunca deve expor a API key do tenant ao JS do browser. Next.js (Pages Router) atua como BFF, guardando a API key num cookie httpOnly cifrado no servidor.

**Decisão**:
1. `cookieCipher.ts` — AES-256-GCM autocontido em `apps/dashboard` (NÃO reimporta `AesGcmCipher` de `apps/api` — evita acoplar dois processos deploáveis separadamente). Novo env var `DASHBOARD_SESSION_SECRET`, deliberadamente separado de `WHATSAPP_CREDENTIALS_MASTER_KEY` (domínios de segurança diferentes).
2. `dashboardSession.ts` — cookie `wa_dashboard_session`, `HttpOnly` + `SameSite=Lax` sempre, `Secure` só em produção, TTL 12h. `requireSession(req, res)` centraliza "ler sessão ou já responder 401" — usado por todas as ~7 rotas protegidas.
3. `apiClient.ts` (servidor) — `API_BASE_URL` (SEM prefixo `NEXT_PUBLIC_`, nunca vai para o bundle do browser) + `callApi()` injeta `X-API-Key` a partir da sessão; path sempre `/api/tenants/:tenantId/whatsapp-sessions...` com `tenantId` vindo SÓ da sessão (nunca de um parâmetro solto) — fecha, do lado do BFF, a mesma classe de IDOR que `requireApiKey`/`resolveTenantFromApiKey` já fecham do lado da API.
4. SSE via POLLING (~2s, `SSE_POLL_INTERVAL_MS`) sobre os endpoints REST já existentes — NÃO push real de Domain. Trade-off de latência (1-3s) aceito conscientemente para não tocar `SessionManager`/`WhatsAppConnectionRegistry` além do que a Fase 2 já tocou (implementar push real exigiria um novo membro em `WhatsAppProviderEvent` + uma nova porta `SessionEventPublisher`). `runSsePoller()` centraliza o protocolo SSE (headers, formato `data:`, heartbeat, encerramento em `req.on('close')`); tolera falha transitória de UMA chamada sem derrubar a conexão (`event: error`, mantém pollando).
5. Login (`POST /api/auth/login`) reaproveita `GET .../whatsapp-sessions` (Fase 1) para validar a API key — nenhum endpoint novo "verify-api-key" em `apps/api` (fora do escopo desta Fase, que é só BFF).
6. 10 rotas Pages Router novas — todas proxy fino (repassam status/body de `callApi()`); rotas SSE exportam `config.api.externalResolver = true` (evita o aviso do Next em dev para conexões longas).
7. `jest.config.js` migrado de config única para multi-projeto (`api`/`dashboard`) — o projeto `api` reproduz exatamente o comportamento antigo (zero regressão); `apps/dashboard/tsconfig.json` ganhou `exclude: ["tests"]`, espelhando `apps/api/tsconfig.json`.

**Consequências**: `.env.example`/`docker-compose.yml` atualizados (`API_BASE_URL` no lugar de `NEXT_PUBLIC_API_URL` — a variável antiga era um bug latente: `localhost` dentro do container do dashboard nunca alcançaria o container da API). Limitação aceita e documentada: `stream`/`qrcode`/`remove`/`history` são segmentos de path reservados sob `/sessions/:sessionName/` (uma sessão chamada literalmente `stream` nunca seria alcançável via essas rotas) — mesma categoria de trade-off já aceita para nomes reservados. 325/325 testes (43 suítes, 2 projetos Jest), `tsc`/`next build` limpos (confirmado pelo usuário).

Migração completa para ESLint 9/flat config fica registrada como item futuro (ver Riscos), não decidida de forma incidental nesta auditoria.

## 54. 2026-07-09 – Propriedade de socket e envio outbound em topologia multiprocesso (Milestone 3)

**Status**: Accepted (decisão de arquitetura; nenhuma linha de código implementada — implementação autorizada a partir do Bloco 1 da Milestone 3, mediante nova aprovação explícita)

**Context**: A Milestone 3 introduz um worker BullMQ em processo separado (`apps/worker`) para gerar respostas de IA de forma assíncrona (ver `MILESTONE_003_AI_AUTORESPONDER.md` §2.5, Alternativa B recomendada — processo separado da API). O `WhatsAppConnectionRegistry` (Application, `apps/api`) é um `Map` em memória, válido **só dentro do processo que o instancia** — os sockets Baileys vivos existem exclusivamente no processo `apps/api`. O plano original da M3 (Bloco 4) assumia que o worker enviaria a resposta gerada "via `WhatsAppProvider.sendMessage()`, resolvido via `WhatsAppConnectionRegistry.getOrCreate()`, já existente" — mas essa chamada, executada no processo do worker, criaria uma instância **nova** de `SessionManager`/`BaileysProvider`, cujo `connect()` abriria um **segundo socket Baileys para o mesmo número de WhatsApp**, já conectado no processo da API. Isso é exatamente o cenário que a ADR #16 ("coordenação distribuída entre pods") identificou como não tratado e bloqueante para múltiplas instâncias — só que a topologia recomendada pela própria M3 o tornaria **certo de acontecer**, mesmo em deploy de instância única, e não apenas um risco teórico de multi-pod. Revisão arquitetural dedicada avaliou três alternativas (worker publica comandos outbound consumidos pela API; coordenação distribuída de posse via lease/lock — implementação completa da ADR #16; worker no mesmo processo da API) antes de qualquer código do Bloco 1. Aprovada explicitamente pelo usuário: Alternativa A.

**Decisão**:
1. O worker BullMQ (`apps/worker`) **nunca** importa, instancia ou depende, direta ou indiretamente, de `WhatsAppConnectionRegistry`, `WhatsAppProvider` ou qualquer implementação concreta de socket. Sua única superfície de saída para o canal WhatsApp é um novo port do Domain, `OutboundMessageDispatcher` (`services/whatsapp/domain/`), com uma única responsabilidade: publicar um comando de envio (`{ tenantId, sessionName, conversationId, messageId, content, idempotencyKey }`) — sem saber como, onde, nem por qual processo esse comando será atendido.
2. `OutboundMessageDispatcher` é implementado na Infrastructure via uma fila BullMQ dedicada (`whatsapp-outbound`), seguindo exatamente o mesmo padrão já aprovado para `AiReplyScheduler`/`BullMqAiReplyScheduler` (Bloco 4 do plano de M3): port no Domain, implementação concreta na Infrastructure, nenhum detalhe de fila vazando para `ai`/`conversations`.
3. `apps/api` — o único processo que instancia `WhatsAppConnectionRegistry` e mantém sockets vivos — ganha um novo componente, `OutboundCommandConsumer` (Infrastructure de `services/whatsapp`, instanciado DENTRO do próprio processo `apps/api`, nunca em `apps/worker` nem em processo à parte), que consome `whatsapp-outbound`, resolve a sessão via `Registry.getOrCreate()` — seguro aqui, pois este é o mesmo processo dono do socket — e chama `WhatsAppProvider.sendMessage()`.
4. `ConversationAiService`/o worker de IA dependem apenas de `OutboundMessageDispatcher`; nenhuma mudança de contrato é exigida de `WhatsAppProvider`, `SessionManager` ou `WhatsAppConnectionRegistry` para viabilizar esta decisão, além da adição aditiva de `sendMessage()` ao port `WhatsAppProvider` já prevista no Bloco 1 do plano de M3. **Achado técnico registrado para o desenho do Bloco 4** (não resolvido nesta ADR): `SessionManager` hoje não expõe nenhum método de envio — `OutboundCommandConsumer` precisará de um novo método nesta classe (ex.: um `sendMessage(content)` que delega a `provider.sendMessage()`), sem receber `tenantId`/`sessionName`/`sessionId` como parâmetro, para permanecer consistente com a restrição fixada pela ADR #29 ("`init()`/`getStatus()`/`disconnect()` nunca devem voltar a aceitar um parâmetro de identidade").
5. A coordenação distribuída completa de posse de socket entre múltiplas réplicas de API (Alternativa B avaliada — lease/lock distribuído, Registry distribuído) permanece **fora do escopo desta ADR e da Milestone 3**, consistente com a ADR #16 (Deferred). Esta ADR não a substitui nem a antecipa — apenas garante que, quando ela for necessária (deploy real com múltiplas réplicas de `apps/api`), a mudança fique inteiramente contida em `services/whatsapp/infrastructure` (trocar o `OutboundCommandConsumer` único por um consumidor com verificação de lease), sem tocar `ai`, `conversations` ou o worker de IA.
6. A Alternativa C (worker no mesmo processo da API) foi avaliada e rejeitada explicitamente: resolveria o bloqueador imediato, mas reacopla permanentemente a escala de geração de IA à escala de conectividade WhatsApp, contrariando o objetivo já registrado no `MILESTONE_003_AI_AUTORESPONDER.md` de preparar a arquitetura para SaaS multi-tenant de larga escala evitando refatorações futuras.

**Consequências**:
- Nenhuma mudança de contrato em `WhatsAppProvider`/`SessionManager`/`WhatsAppConnectionRegistry` além da já prevista no Bloco 1 da M3 (`sendMessage()`, `message_received`) e do novo método de envio em `SessionManager` (decisão 4).
- Uma nova fila (`whatsapp-outbound`) e um novo port (`OutboundMessageDispatcher`) foram incorporados ao desenho do Bloco 4 do `MILESTONE_003_AI_AUTORESPONDER.md` (atualizado nesta mesma rodada, ver `PROJECT_STATUS.md`).
- Idempotência do comando outbound (evitar reenvio em caso de reprocessamento da fila) precisa de uma chave de dedup dedicada — tratamento a formalizar antes do Bloco 4 (não implementada nem detalhada nesta ADR).
- `apps/api` passa a rodar dois papéis internos (servidor HTTP + `OutboundCommandConsumer`) — mesmo padrão de múltiplos entrypoints dentro de um processo já aceitável (não introduz um terceiro artefato de deploy).
- **Risco identificado nesta rodada, não resolvido**: `OutboundCommandConsumer` depende de a sessão já estar viva no `Registry` do processo `apps/api`. Se a API reiniciou e nenhuma chamada HTTP reconectou a sessão ainda (P3 — bootstrap/recuperação pós-restart, Architecture Review original de 2026-07-06, ainda Deferred), `getOrCreate()` devolveria um `SessionManager` cujo provider nunca chamou `connect()` — o envio falharia sobre um socket inexistente. Este ponto precisa de decisão explícita antes do Bloco 4 (reconectar on-demand dentro do consumer, ou falhar o job com retry até a sessão ser reconectada por outro caminho) — P3 deixa de ser um risco só de UI de status e passa a afetar a entrega de mensagens automatizadas.
- Quando uma futura necessidade real de múltiplas réplicas de `apps/api` surgir, a implementação da coordenação distribuída (ADR #16) deve ser tratada como sua própria sub-entrega, não incidental a nenhuma outra milestone — mesma recomendação já registrada na ADR #16, agora reafirmada.
- Nenhum conflito encontrado com nenhuma ADR anterior (#1–#53) — auditoria completa registrada em `PROJECT_STATUS.md`.

## 55. 2026-07-10 – Milestone 3, Bloco 4: topologia do worker, idempotência outbound, ordem de criação da Message e comportamento sem sessão viva

**Status**: Accepted, implementado

**Context**: A ADR #54 resolveu a fronteira estrutural (worker nunca toca sockets), mas deixou explicitamente quatro pontos como "achado aberto, decisão necessária antes do Bloco 4" (§2.5/§2.8 do `MILESTONE_003_AI_AUTORESPONDER.md`): (D1) onde o worker de IA vive fisicamente no monorepo; (D2) qual a chave de idempotência do comando outbound; (D3) em que momento a `Message` outbound é criada; (D4) o que `OutboundCommandConsumer` faz quando a sessão não está viva no `Registry` do processo. As quatro foram levantadas com alternativas e recomendação, apresentadas ao usuário via pergunta de múltipla escolha, e confirmadas — todas na opção recomendada — antes de qualquer linha de código do Bloco 4 ser escrita, seguindo a mesma disciplina já usada em todos os blocos anteriores desta Milestone.

**Decisão**:
1. **D1 — topologia do worker**: `apps/api/src/worker.ts`, MESMO pacote/workspace de `apps/api` — não um workspace npm `apps/worker` separado, como um esboço textual anterior do `MILESTONE_003_AI_AUTORESPONDER.md` (§2.5-B) sugeria de forma ambígua (o mesmo documento, em outras seções — §2.8/§3-Bloco4 — já tratava `apps/worker` como se fosse um pacote distinto, uma inconsistência textual real encontrada nesta rodada). Reaproveita diretamente todo o código de `services/ai/`/`services/conversations/` já existente, sem precisar extrair um novo workspace `packages/` compartilhado só para isso — sobe como processo Node SEPARADO do `index.ts` (mesma imagem Docker, `CMD`/entrypoint diferente, ver decisão do Bloco 4e abaixo), preservando o objetivo de escala independente que motivou a ADR #54.
2. **D2 — chave de idempotência do comando outbound (fila `whatsapp-outbound`)**: `aiInteractionId` (o `id` devolvido por `AiInteractionRepository.record()`, achado F2 já aprovado antes deste bloco) usado como `jobId` nativo do BullMQ. Cada `AiInteraction` bem-sucedida produz no máximo uma tentativa de envio — reaproveita uma relação 1:1 que já existia no desenho do Bloco 3b, sem introduzir um identificador novo só para este propósito.
3. **D3 — momento de criação da `Message` outbound**: só DEPOIS do envio via `SessionManager.sendMessage()` ter sucesso, nunca antes. Consequência direta: `OutboundMessageCommand` não pode carregar um `messageId` (a `Message` ainda não existe no momento em que o comando é despachado) — carrega `aiInteractionId` em seu lugar.
4. **D4 — sessão sem conexão viva no processo**: `OutboundCommandConsumer` FALHA o job (nunca chama `sessionManager.init()`/reconecta on-demand) — deixa o BullMQ reter/reprocessar via seu mecanismo nativo de retry/backoff, até que a sessão seja reconectada por outro caminho (ex.: uma chamada HTTP ao módulo WhatsApp). Implementado "de graça": `OutboundCommandConsumer.consume()` só chama `registry.getOrCreate()` (pooling puro, sem efeito colateral) + `sessionManager.sendMessage()`, que naturalmente lança `WhatsAppNotConnectedError` se o provider nunca chamou `connect()` nesta instância de processo.

**Decisões de design adicionais, tomadas durante a implementação (não eram alternativas em aberto no levantamento, mas registradas aqui por completude)**:
- **Simplificação do payload de `OutboundMessageCommand`**: reduzido do esboço original do `MILESTONE_003_AI_AUTORESPONDER.md` (`{ tenantId, sessionName, conversationId, messageId, content, idempotencyKey }`) para `{ tenantId, conversationId, aiInteractionId, content }`. `sessionName`/o JID do destinatário são resolvidos por `OutboundCommandConsumer` via `ConversationRepository.findById(conversationId)` no momento de processar, em vez de viajarem no payload do job — evita uma segunda fonte de verdade que poderia divergir da primeira (ex.: uma `Conversation` reatribuída a outro `sessionName` entre o agendamento e o processamento), mesmo racional já usado pela re-checagem de `shouldAutoRespond()`. `messageId`+`idempotencyKey` foram substituídos por um único campo, `aiInteractionId` (decisões D2/D3 acima).
- **`AiReplyJobProcessor`** (`services/ai/application/AiReplyJobProcessor.ts`, novo): a orquestração de UM job da fila `ai-reply` (buscar conversa, re-checar `shouldAutoRespond()`, buscar histórico via `MessageRepository.listRecentByConversation()` e inverter para ordem cronológica, chamar `ConversationAiService.generateReply()`, despachar via `OutboundMessageDispatcher` quando `status === 'success'`) foi extraída de `worker.ts` para uma classe própria, testável com Fakes (sem Redis/BullMQ real) — mesma separação já usada em toda a Milestone 3 entre "regra de orquestração" e "wiring de infraestrutura". `worker.ts` ficou reduzido a: carregar env, construir as dependências reais (Prisma, `AiProviderFactoryImpl`, filas BullMQ), instanciar `AiReplyJobProcessor` e ligá-lo a um `bullmq.Worker`, mais logging de `completed`/`failed` (critério de aceite do §5 do `MILESTONE_003_AI_AUTORESPONDER.md` — "fila sem observabilidade vira caixa-preta") e encerramento gracioso via `SIGTERM`/`SIGINT`.
- **`AI_HISTORY_LIMIT`** (nova variável de ambiente, opcional, default 20 mensagens): quantas mensagens recentes da conversa entram no histórico enviado ao provider de IA a cada job. Não estava especificada em nenhum critério de aceite do documento de arquitetura da Milestone — é uma decisão de implementação do Bloco 4, não do levantamento arquitetural; o valor 20 é um ponto de partida razoável, não validado por dados reais de uso (registrado explicitamente como tal na docstring de `AiReplyJobProcessor.ts`).

**Consequências**:
- Nenhuma mudança de contrato em `WhatsAppProvider`/`WhatsAppConnectionRegistry` além do já previsto (`SessionManager.sendMessage()`, Bloco 4a).
- `worker.ts` usa imports ESTÁTICOS (diferente do `import()` dinâmico de `mountWhatsAppSessionsRoutes()` em `index.ts`): nenhum teste importa `worker.ts` (a lógica testável já foi extraída para `AiReplyJobProcessor`), e nenhum dos imports de `worker.ts` toca Baileys/ESM puro — garantia adicional, por construção, da fronteira da ADR #54 (nenhum caminho de import de `worker.ts` alcança `WhatsAppConnectionRegistry`/`WhatsAppProvider`).
- Risco residual aceito, documentado (não corrigido, mesmo espírito do risco já registrado em `OutboundCommandConsumer`, Bloco 4c): um job `ai-reply` reentregue pelo BullMQ (retry) reexecuta `AiReplyJobProcessor.process()` do zero, gerando uma nova tentativa e um novo `AiInteraction` — a deduplicação de ENVIO (não de geração) é responsabilidade só do `jobId` da fila `whatsapp-outbound` (D2), que não cobre duas gerações distintas para o mesmo job `ai-reply` reentregue. Corrigir isso de verdade exigiria uma chave de idempotência derivada de `tenantId`+`conversationId`+`messageId` (o payload original de `AiReplyJobData`), checada ANTES de gerar uma nova resposta — não implementado agora (YAGNI, mesmo racional já registrado no Bloco 3b/F1).
- Nenhum conflito encontrado com nenhuma ADR anterior (#1–#54).

## 56. 2026-07-10 – Bloco 4: achados de ambiente/tooling (corrupção adicional do Prisma Client no sandbox; divergência de versão do `ioredis`)

**Status**: Accepted, implementado (correção do `ioredis`); documentado sem correção possível neste ambiente (corrupção do Prisma Client)

**Context**: Dois achados de ambiente/dependências surgiram durante a implementação do Bloco 4, nenhum relacionado a uma decisão arquitetural — registrados aqui pelo mesmo princípio já aplicado na ADR #53 ("tooling, não arquitetura, mas relevante o suficiente para registro formal").

**Achado 1 — corrupção adicional do Prisma Client, sandbox-only**: `npm install bullmq`/`npm install ioredis` (Bloco 4b) disparou o postinstall automático de `@prisma/client`, que leu uma visão do `prisma/schema.prisma` truncada pelo mesmo bug de dessincronização do mount FUSE já disclosed em rodadas anteriores desta sessão (edições de arquivo confirmadas corretas via a ferramenta de leitura, mas vistas truncadas por um tempo pela camada de execução de shell) — e regenerou `node_modules/.prisma/client` a partir dessa versão truncada, perdendo as adições de `AiInteraction`/`AiProviderType`/`AiInteractionStatus` do Bloco 3b no client gerado. Todas as tentativas de regeneração dentro do sandbox (`npx prisma generate`, `npm rebuild @prisma/client prisma`, invocação direta do script de postinstall) falharam por bloqueio de rede a `binaries.prisma.sh` (já um limitador pré-existente e disclosed, não novo). **Decisão**: aceitar e documentar, não é corrigível neste ambiente. **Impacto medido**: `tsc --noEmit`/`npm run build` de `apps/api` falham com exatamente 4 erros, todos confinados a `PrismaAiInteractionRepository.ts` (dois `TS2305` de membros não exportados, dois `TS2339` de propriedade `aiInteraction` ausente no client). Zero impacto em `npm test` (todo arquivo que toca o Prisma Client usa exclusivamente `import type`, apagado pelo `ts-jest` sob `isolatedModules: true` — o client corrompido nunca é de fato importado em tempo de execução dos testes). Irrelevante na máquina real do usuário, onde `npm install`/`npx prisma generate` têm acesso de rede normal.

**Achado 2 — divergência de versão do `ioredis` entre `apps/api` e a dependência interna do `bullmq`**: `apps/api/package.json` declarava `"ioredis": "^5.11.1"` (adicionado no Bloco 4b, antecipando a construção de conexões em `worker.ts`); `bullmq` declara internamente `"ioredis": "5.10.1"` (exato). Como as duas versões não coincidiam, o `npm install` não conseguiu deduplicar — `apps/api/node_modules/ioredis` (5.11.1) e a cópia hoisted na raiz (5.10.1, satisfazendo `bullmq`) coexistiam como dois pacotes fisicamente distintos. Isso é um problema real de higiene de dependências, não um artefato do sandbox: mesmo numa máquina limpa, `npm install` teria produzido a mesma duplicação. `tsc` acusou o sintoma: `new IORedis(...)` (nossa cópia) não era atribuível ao parâmetro `connection` de `Queue`/`Worker` do BullMQ (que espera uma instância da SUA PRÓPRIA cópia de `ioredis`) — erro estrutural `TS2322`, incluindo um `protected` de `AbstractConnector` incompatível entre as duas cópias do mesmo pacote. **Decisão**: fixar `apps/api`'s `ioredis` na MESMA versão exata que `bullmq` usa internamente (`"5.10.1"`, sem `^`) e rodar `npm dedupe` para forçar a reconciliação em uma única cópia hoisted na raiz. **Alternativa descartada**: parar de construir instâncias `IORedis` próprias e passar só um objeto plano de configuração (`{ host, port, ... }`) para `connection:`, deixando o BullMQ construir seus próprios clientes internamente — tecnicamente mais simples e elimina a categoria inteira de problema, mas descartada porque `worker.ts` precisa fechar as conexões explicitamente no desligamento gracioso (`SIGTERM`/`SIGINT`), o que é mais direto tendo a referência à instância `IORedis` em mãos; fica registrada como alternativa válida caso esta classe de problema volte a aparecer no futuro (ex.: ao adicionar um terceiro consumidor BullMQ).

**Consequências**:
