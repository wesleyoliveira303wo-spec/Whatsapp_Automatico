# WhatsApp Integration Documentation

Documentation for the **WhatsApp** connectivity layer.

- **Current implementation**: QR code login usando **Baileys** (ver `DECISIONS.md`, item 10). Milestone 1, Item 3: `BaileysProvider` (`apps/api/src/services/whatsapp/infrastructure/providers/baileys/BaileysProvider.ts`) implementa `WhatsAppProvider` de verdade — recebe `tenantId`/`sessionName`/`CredentialsStore`/`Logger` no construtor (uma instância = um socket = uma sessão). `BaileysCredentialsAdapter.ts` (mesma pasta) bridgeia `CredentialsStore` (genérico) para o `AuthenticationState` esperado pelo Baileys — só a Infrastructure sabe que Baileys existe. Ver ADR #22. **Ainda não instalado/rodado de fato** (`npm install`/`tsc`/`npm test` pendentes de confirmação local, sandbox sem shell).
- **Interface (port)**: `WhatsAppProvider` (`apps/api/src/services/whatsapp/domain/providers/WhatsAppProvider.ts`) define `connect()`, `disconnect()`, `getStatus()`, `getQRCode()`, `getPhoneNumber()` e `onEvent(listener)`. `sendMessage()`/`receiveMessage()` ainda não fazem parte do contrato — serão adicionados quando o envio/recebimento de mensagens entrar no roadmap (fora do escopo do item atual, para não antecipar decisões de mensageria).
- **`onEvent`**: canal assíncrono genérico para o provider notificar eventos que não resultam de uma chamada direta da Application. Recebe `WhatsAppProviderEvent` (`.../domain/providers/WhatsAppProviderEvent.ts`), uma união discriminada por `type` — hoje só `'status_changed'`, mas pensada para crescer (`qr_updated`, `message_received`, `presence_updated`) sem exigir novo método no port a cada nova capacidade (substitui `onStatusChange`/`WhatsAppProviderStatusUpdate`, que só suportava um tipo de evento — ver ADR #14, achado F2 do Architecture Gate Review).
- **Application**: `SessionManager` (`apps/api/src/services/whatsapp/application/SessionManager.ts`) orquestra conectar/desconectar/status usando apenas o port acima — não conhece Baileys nem qualquer detalhe de Infrastructure. `init()` reaproveita/atualiza a sessão existente ao reconectar (nunca cria duplicata — ver `@@unique([tenantId, sessionName])` em `prisma/schema.prisma`) e assina `onEvent` (via `subscribeToProviderEvents`) — **antes de chamar `connect()`** (ver ADR #23, BUG-01) — para manter o registro atualizado após retornar, ignorando (early return) qualquer tipo de evento que ainda não reconheça. O "reaproveitar sem reconectar" só acontece quando `provider.getStatus()` (não o banco isoladamente) confirma que já existe conexão viva NESTE processo (ADR #23, BUG-02) — importante depois de um restart do servidor. **Atualizado (Item 5, Bloco 3 — ADR #29)**: `SessionManager` não aceita mais `tenantId`/`sessionName`/`sessionId` como parâmetros soltos em `init()`/`getStatus()`/`disconnect()` — recebe uma única `WhatsAppSessionKey` (Value Object, ADR #33) no construtor, fixada para toda a vida da instância. O antigo `WhatsAppSessionOwnershipError`/`assertOwnsSession` (ADR #23, BUG-03) foi REMOVIDO: o problema que mitigava em runtime tornou-se estruturalmente impossível, já que não há mais nenhum identificador externo para divergir do que a instância gerencia. Quem cria/reaproveita instâncias por `(tenantId, sessionName)` é o `WhatsAppConnectionRegistry` (ADR #36).
- **Persistência**: `prisma/schema.prisma` (models `Tenant`, `WhatsAppSession`, enums `WhatsAppSessionStatus` e `WhatsAppProviderType`) — adicionado na Milestone 1, Item 2, coexistindo no mesmo arquivo com o domínio legado "Conversations" (migração adiada, ver `DECISIONS.md` ADR #11). `provider` é enum (hoje só `BAILEYS`) desde a ADR #15 (achado F6).
- **Logging (M1A.1)**: `SessionManager` recebe um `Logger` (`apps/api/src/shared/domain/Logger.ts`) como dependência obrigatória do construtor — port compartilhado entre bounded contexts (não exclusivo do WhatsApp), com implementações `ConsoleLogger` (dev) e `NoopLogger` (Null Object, para testes/consumidores que não querem logging real) em `apps/api/src/shared/infrastructure/logging/`. Loga início/conclusão de `init()`, reaproveitamento de sessão já conectada, `disconnect()`, consultas a sessão inexistente e falhas ao persistir atualizações assíncronas do provider (ver ADR #13).
- **Future migration**: Plano de troca para WhatsApp Cloud API (`CloudAPIProvider`) continua válido — basta uma nova classe implementando `WhatsAppProvider`.
- **Persistência de credenciais (M1A.6, ADR #21)**: `CredentialsStore` (`apps/api/src/shared/security/domain/CredentialsStore.ts`) é um port genérico de chave-valor por tenant (`get`/`getAll`/`set`/`remove`/`clear`, endereçado por `tenantId` + `namespace` + `key`) — deliberadamente sem nenhum conceito de WhatsApp, para não vazar o formato interno do Baileys (que não é um blob único, e sim várias entradas do protocolo Signal) para o Domain. Composto com o port `Cipher` (`.../shared/security/domain/Cipher.ts`, `encrypt`/`decrypt` por tenant) para criptografia em repouso. Implementações em `shared/security/infrastructure/`: `AesGcmCipher` (AES-256-GCM, chave derivada por tenant via HKDF) e `PrismaCredentialsStore` (model `TenantCredential`, sem FK para `WhatsAppSession`). O futuro `BaileysProvider` (Item 3) vai consumir `CredentialsStore` diretamente para adaptar o formato esperado pelo `SignalKeyStore` do Baileys — esse mapeamento fica inteiramente na Infrastructure.
- **Repositório (Item 4, ADR #24)**: `PrismaWhatsAppSessionRepository` (`apps/api/src/services/whatsapp/infrastructure/repositories/PrismaWhatsAppSessionRepository.ts`) implementa `WhatsAppSessionRepository` sobre o model `WhatsAppSession`, com mapeamento explícito entre os literais do Domain (`'connected'`) e os valores do enum Prisma (`'CONNECTED'`). `update()` em registro inexistente (P2025) resolve silenciosamente (no-op), espelhando o Fake já usado nos testes do `SessionManager`.
- **Concorrência em `init()` (P6, ADR #25)**: `SessionManager.init()` usa `WhatsAppSessionRepository.upsertByTenantAndSessionName()` — uma operação atômica no banco (`INSERT ... ON CONFLICT DO UPDATE` no Postgres) — em vez de ler e depois criar/atualizar separadamente. Isso fecha a janela de corrida entre duas chamadas concorrentes de `init()` para a mesma `tenantId`+`sessionName`: a que "perde" a corrida converge para a mesma linha que a vencedora já criou, em vez de duplicar o registro ou lançar uma exceção de violação de unicidade não tratada. O `id` definitivo de uma sessão é sempre o retorno desse upsert, nunca um `id` gerado especulativamente antes da chamada.
- **Ciclo de vida do socket em `creds.update` e logout (auditoria de integração, ADR #26)**: o handler `creds.update` de `BaileysProvider` usa o mesmo guard de identidade (`this.socket !== socket`) já aplicado a `connection.update` (BUG-04) — sem isso, um evento `creds.update` tardio de um socket já substituído numa reconexão rápida podia sobrescrever credenciais mais novas com dados stale (BUG-12, corrigido). Além disso, ao detectar `DisconnectReason.loggedOut` em `connection.update`, o provider agora chama `credentialsStore.clear(tenantId, namespace)` — sem essa limpeza, um logout real deixava credenciais inválidas persistidas, que seriam recarregadas na próxima tentativa de reconexão em vez de gerar um QR novo (BUG-13, corrigido). Ambas as falhas de persistência/limpeza são logadas via `.catch()`, nunca lançadas para o chamador do evento.
- **Session management**: Tokens stored encrypted in Redis; TTL 24h.
- **Rate limiting**: Outbound messages limited per tenant to comply with WhatsApp policies.
