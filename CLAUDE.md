## 1. Visão Geral do Projeto <a name="visão-geral-do-projeto"></a>

- **Objetivo:** Construir uma plataforma de automação inteligente para WhatsApp que vá além de um mero disparador de mensagens, oferecendo um **CRM inteligente** com IA.
- **Propósito:** Auxiliar pequenas e médias empresas a prospectar, atender e nutrir leads via WhatsApp de forma automatizada, porém com intervenção humana quando necessário.
- **Visão de Longo Prazo:** Evoluir de uma aplicação local para um **SaaS multi‑tenant**, suportando múltiplas empresas, números de WhatsApp, agentes de IA e integrações externas.
- **Filosofia do Projeto:** **Valor entregue primeiro**, **arquitetura evolutiva**, **documentação viva** e **qualidade como baseline**.
- **Público‑Alvo:** Startups, agências de marketing e times de vendas que já utilizam WhatsApp como canal principal de comunicação.
- **Principais Funcionalidades:**
  - Conexão via QR Code (WhatsApp Web API).
  - Gerenciamento de sessões múltiplas.
  - Importação de listas de leads (CSV/Excel).
  - Criação e agendamento de campanhas.
  - Mensagens personalizadas com templates.
  - Respostas automáticas usando IA (Claude, GPT, Gemini).
  - Escalonamento para atendimento humano.
  - Histórico completo de conversas.
  - Painel administrativo moderno.
  - Métricas e analytics em tempo real.
  - Banco de conhecimento para IA (FAQ, documentos).
  - Preparação para multi‑usuário e multi‑empresa.

## 5. Arquitetura Geral <a name="arquitetura-geral"></a>

```
[Frontend] <--REST/GraphQL--> [API Gateway] <--gRPC/Message Queue--> [Backend Services]
        |                                   |
        |                                   +--[IA Service] (Claude, outros)
        |                                   |
        |                                   +--[WhatsApp Service] (WebSocket + QR)
        |                                   |
        |                                   +--[Scheduler] (BullMQ / Agenda)
        |                                   |
        +--[Auth Service] (JWT, OAuth2)   +--[Analytics Service] (Prometheus, Grafana)

[Database] <-- Prisma ORM --> PostgreSQL
[Message Queue] <-- Redis --> BullMQ
[Cache] <-- Redis -->
```

- **Frontend:** Next.js (React) + Tailwind + shadcn/ui – SPA com SSR para SEO interno.
- **Backend (API Gateway):** Node.js + Express (type‑safe) expose GraphQL/REST.
- **Serviços:** Cada domínio como micro‑service leve (WhatsApp, IA, CRM, Scheduler, Analytics, Auth).
- **Fila:** Redis + BullMQ para jobs de disparo de mensagens, retries, e análises.
- **IA:** Wrapper service que escolhe provedor (Claude default) e permite troca futura.
- **WhatsApp:** Integração via **WhatsApp Web** (WebSocket) ou **WhatsApp Cloud API** (quando disponível).
- **Scheduler:** Agendamento de campanhas, reminders, e limpeza de dados.
- **Analytics:** Coleta de eventos, armazenamento em PostgreSQL + visualização via Grafana.
- **Future SaaS:** Multi‑tenant via _tenantId_ nas tabelas, isolamento de dados e uso de sub‑domínios.

## 8. Convenções de Código <a name="convenções-de-código"></a>

- **Nomenclatura:** `camelCase` para variáveis/functions, `PascalCase` para classes/componentes, `snake_case` apenas para nomes de bancos.
- **Arquivos:** Extensões `.ts` (backend) e `.tsx` (frontend). Um único export default por arquivo.
- **Imports:** Ordem: React, libs externas, aliases internas, relativos. Linhas vazias entre grupos.
- **Exports:** Preferir named exports; default apenas para componentes React.
- **Aliases:** Definidos em `tsconfig.json` (`@frontend/*`, `@backend/*`, `@shared/*`).
- **Comentários:** Apenas _porquê_; evitar comentários óbvios.
- **Tratamento de Erros:** `try/catch` centralizado em middlewares; erros customizados (`AppError`).
- **Logs:** Winston com níveis (`info`, `warn`, `error`), correlacionados a requestId.
- **Lint/Prettier:** Configurações padrão do Airbnb + Prettier; rodar `npm run lint` antes de commit.
- **Commit Guidelines:** Conventional Commits (`feat:`, `fix:`, `docs:` etc.).

## 9. Design System <a name="design-system"></a>

| Aspecto            | Regra                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------- |
| **Componentes**    | Baseados em shadcn/ui; cada componente tem _variant_ e _size_ padronizados.                       |
| **Responsividade** | Mobile‑first; breakpoints: `sm` (640px), `md` (768px), `lg` (1024px), `xl` (1280px).              |
| **Acessibilidade** | ARIA attributes, foco visível, contraste ≥ 4.5:1 (WCAG AA).                                       |
| **Tema**           | Sistema de tokens (core colors, radii, spacing) via Tailwind `theme.extend`.                      |
| **Cores**          | Primária: `#0A74DA` (Anthropic blue); secundária: `#0065FF`; neutrals: `gray-50`‑`gray-900`.      |
| **Tokens**         | `spacing`: 0‑64 (multiples of 4). `borderRadius`: `sm`, `md`, `lg`.                               |
| **Tipografia**     | Font: Inter (system fallback). Tamanhos: `sm` 0.875rem, `base` 1rem, `lg` 1.125rem, `xl` 1.25rem. |
| **Reutilização**   | Cada UI pattern (button, card, modal) tem um _compound component_.                                |

## 10. Banco de Dados <a name="banco-de-dados"></a>

### Modelo Inicial (ER)

- **User** (`id`, `name`, `email`, `passwordHash`, `role`, `tenantId`)
- **Tenant** (`id`, `name`, `plan`, `createdAt`)
- **WhatsAppSession** (`id`, `qrCode`, `status`, `createdAt`, `updatedAt`, `tenantId`)
- **Lead** (`id`, `name`, `phone`, `source`, `status`, `createdAt`, `tenantId`)
- **Campaign** (`id`, `name`, `templateId`, `schedule`, `status`, `ownerId`, `tenantId`)
- **MessageTemplate** (`id`, `name`, `content`, `variables`, `tenantId`)
- **Conversation** (`id`, `leadId`, `sessionId`, `startedAt`, `endedAt`)
- **Message** (`id`, `conversationId`, `direction` (`IN/OUT`), `content`, `sentAt`, `aiGenerated`)
- **AnalyticsEvent** (`id`, `type`, `payload`, `timestamp`, `tenantId`)
- **KnowledgeBase** (`id`, `title`, `content`, `embeddingVector`, `tenantId`)

### Estratégia de Crescimento

- **Multi‑tenant:** Cada tabela possui `tenantId` (FK) para isolamento.
- **Sharding futuro:** Partitionamento por `tenantId` quando número de tenants > 1000.
- **Indexes críticos:** `phone` (Lead), `status` (Campaign), `createdAt` (Message), `tenantId` + `id` (todos).
- **Migrations:** Prisma migrates, versionadas no Git.

| **Auth**                 | JWT + Refresh, bcrypt, 2FA opcional, OIDC gateway futuro.                              |

## 16. Escalabilidade <a name="escalabilidade"></a>

- **Multi‑user / Multi‑tenant** – `tenantId` nas tabelas, middleware que injeta contexto.
- **Múltiplos números WhatsApp** – Cada `WhatsAppSession` tem seu próprio container/worker.
- **Agentes de IA** – Pool de workers, cache de embeddings no Redis.
- **Campanhas simultâneas** – BullMQ com _concurrency_ configurável; back‑pressure.
- **Horizontal scaling** – Docker Compose → Kubernetes; serviços stateless.
- **Observability** – métricas por tenant, alertas automáticos.

### Milestone 5 — Auth, RBAC e Multiusuário (M5A–M5H-lite)

**Data:** 2026-07-22
**Contexto:** O Dashboard autenticava só com a API key do tenant (plano máquina) — sem conceito de pessoa, cargo ou trilha de responsabilidade.
**Decisão:** Bounded context `services/auth` completo: usuários com senha scrypt (zero dependência), access token HS256 curto + refresh token com rotação e detecção de reuso, RBAC fixo em código (5 cargos, catálogo `Permission` + `hasPermission` + régua `outranks`), trilha de auditoria append-only, gestão de usuários (UserManagementService, hierarquia estrita: só gerencia quem está estritamente abaixo; owner intocável; senha provisória com `must_change_password` + troca obrigatória). `authenticate` dois-planos (Bearer OU X-API-Key) nas rotas de conversas/sessões — API key preservada como plano máquina (ADR #45/#54 intactas). Pendências registradas (M5 completo): viewer de auditoria na UI, CSRF token explícito (mitigado por SameSite=Lax), lockout por conta (mitigado por rate limit por IP), rate limit compartilhado via Redis quando houver multi-instância. Migration nova: `must_change_password` (aditiva, default false). Suíte: 761+ testes.

### Milestone 6 (parcial) — Segundo provider de IA: Gemini (Google) para free tier

**Data:** 2026-07-22
**Contexto:** O autoresponder só tinha o `ClaudeAiProvider` (Anthropic, pago). Preços do Gemini adicionados em `AI_PRICING` (flash-lite/flash/pro) — no free tier o custo real é US$ 0, valores servem para estimar o tier pago.
**Impacto:** Trocar de provider é só `AI_PROVIDER=gemini` + `GEMINI_API_KEY`/`AI_GEMINI_MODEL` no `.env` — zero mudança em `ConversationAiService`/`PromptBuilder`/worker além do wiring. Testes novos: `GeminiAiProvider.test.ts` (9), factory reescrita + cobertura gemini, pricing +1. ### Atendimento humano pela Dashboard: responder + auto-escalonamento + notificação + tempo real (N2)

**Data:** 2026-07-23
**Contexto:** Depois do teste real, três pedidos: (1) responder o cliente PELA Dashboard quando o operador assume; (2) ser NOTIFICADO quando a IA passa o atendimento para um humano (evitar fila de espera); (3) a tela da conversa atualizar em tempo real (o operador tinha de dar F5 para ver a conversa da IA com o cliente). Descoberta-chave durante a análise: a IA dizer "vou encaminhar para um humano" era só TEXTO — nada mudava o estado; a conversa seguia em `bot` e a IA continuava respondendo. Sem um estado real de "aguardando humano", a notificação não teria o que observar.
**Decisão:**

- **Envio pelo operador:** `OutboundMessageCommand` generalizado de forma RETROCOMPATÍVEL — `aiInteractionId` virou opcional e ganhou `idempotencyKey` (UUID) para mensagens de humano; dispatcher usa `aiInteractionId ?? idempotencyKey` como `jobId`; consumer só faz `linkMessage` se houver `aiInteractionId`. Fluxo da IA INTOCADO (sempre passa `aiInteractionId`). Novo `ConversationsService.sendAgentMessage` (valida `human` + ownership, mesma régua de `resume`), rota `POST /conversations/:id/messages` (`message:send`), despacho pela MESMA fila outbound (ordem/socket únicos, ADR #54). `apps/api` passou a ter um produtor da fila `whatsapp-outbound` (antes só o worker produzia). Erro novo `ConversationNotHumanError` → 409. UI: `MessageComposer` na tela de detalhe, visível só quando `status='human'`.
- **Auto-escalonamento (marcador interno):** a IA inclui o marcador `ESCALATION_MARKER` (`[[ESCALAR_HUMANO]]`) quando decide passar para um humano (instrução no `systemPrompt` v1). `extractEscalation` (Domain, `services/ai/domain/escalationSignal.ts`) detecta e REMOVE o marcador (cliente nunca vê); `ConversationAiService` devolve `escalate` no resultado `success` com o `content` já limpo; `AiReplyJobProcessor`, após ENVIAR a mensagem de aviso, coloca a conversa em `human` SEM dono (`assignedToUserId: null`) → entra na fila de espera e a IA para de responder (`shouldAutoRespond` volta false). Comportamento escolhido: "IA avisa e silencia".
- **Notificação:** "aguardando humano" = `status='human'` E sem dono. `useWaitingForHuman` (na Sidebar, montada em toda página protegida) faz polling (~5s), mostra contador (badge vermelho ao lado de "Conversas") e, quando o número SOBE, toca um som (Web Audio, sem asset) + notificação nativa do navegador (`lib/notify.ts`); nunca alarma no 1º carregamento. Lista destaca as linhas aguardando (âmbar + selo "Aguardando atendente").
- **Tempo real (sobrepõe a decisão "SEM SSE" do M3/Bloco 6):** hook `usePollingRefresh` (pausa com a aba oculta, refaz ao voltar) ligado a `useMessagesTimeline`, `useAiInteractions` e `useConversationDetail` (este sem piscar "Carregando" nos polls e sem apagar a conversa em falha transitória). A tela da conversa se atualiza sozinha (~4s).
  **Impacto:** Operador atende de ponta a ponta pela Dashboard; a IA entrega o bastão sozinha e o time é avisado na hora; nada de F5. Fluxo da IA e testes existentes preservados (mudança do outbound é aditiva). `ai_profile`/Gemini intactos. Testes novos/ajustados: OutboundCommandConsumer (+1), BullMqOutboundMessageDispatcher (+1), ConversationsService (+7 sendAgentMessage), escalationSignal (3), ConversationAiService (+1 escalate, +1 ajuste), AiReplyJobProcessor (+2), BFF messages proxy (5). Pendências: idempotência exactly-once do envio segue "at-least-once" (risco de MVP já documentado no OutboundCommandConsumer); notificação por e-mail e permissão de som dependem do navegador/gesto do usuário.

### Bug crítico de entrega: LID (@lid) — responder ao endereço de privacidade não entrega

**Data:** 2026-07-23
**Contexto:** Teste real com um NÚMERO NOVO: a IA gerava a resposta (aparecia na Dashboard, "Gerada por IA"), mas ela NÃO chegava no celular do cliente. Como o `OutboundCommandConsumer` só grava a `Message` DEPOIS de `sendMessage()` não lançar, o fato de a mensagem aparecer na Dashboard provava que o Baileys ACEITAVA o envio — mas não entregava. Restart completo da API não resolveu (descartou a hipótese de "socket zumbi"). O `contact_jid` da conversa era `254352879009802@lid` — formato LID (Linked ID, privacidade do WhatsApp para contas/números novos), não um telefone. `BaileysProvider.handleMessagesUpsert` guardava `key.remoteJid` CRU como `from`; responder ao `@lid` é aceito pelo Baileys mas cai no vazio.
**Decisão:** No `handleMessagesUpsert`, o endereço de resposta passou a ser `jidNormalizedUser(key.senderPn || remoteJid)`. `senderPn` (campo de `WAMessageKey` no Baileys 6.7.23 — a versão REAL instalada, `^6.7.9` resolveu para 6.7.23) traz o número real (`@s.whatsapp.net`) do remetente quando a mensagem vem de um LID; sem LID, é ausente e cai no `remoteJid` de sempre (comportamento inalterado). `jidNormalizedUser` remove sufixo de device/agente. Como a conversa é chaveada por `contactJid`, mensagens de um LID passam a criar/achar a conversa pelo PN (número real) — conversas antigas gravadas com `@lid` ficam órfãs (aceitável). Mock virtual de `@whiskeysockets/baileys` no teste ganhou `jidNormalizedUser` (minimalista) + 2 testes (LID→senderPn; strip de device).
**Impacto:** Envio volta a entregar para números no formato LID (cada vez mais comum, sobretudo contas novas). NÃO era o Gemini nem limite de free tier — a geração sempre funcionou; o problema era só o "envelope" do envio. Pendência: quando o WhatsApp NÃO fornece `senderPn` (ex.: privacidade total, comunidades), ainda cairíamos no `@lid` — mapear LID→PN via `signalRepository` do Baileys fica como evolução se aparecer esse caso. Testes: BaileysProvider 49/49.

### Erro 463 (NackCallerReachoutTimelocked) → upgrade do Baileys 6.7.23 → 7.0.0-rc13 (import dinâmico ESM)

### Cota do Gemini free tier esgotada (429) → fix de modelo + escalonar-em-falha

**Data:** 2026-07-23
**Contexto:** Depois do 463 resolvido, a IA respondeu por um tempo e PAROU. O print da Dashboard ("Interações de IA" com "Erro do provider") mostrou o corpo do erro: `429 RESOURCE_EXHAUSTED`, `quotaMetric: generate_content_free_tier_requests`, `model: gemini-3.6-flash`, `quotaValue: "20"`. Causa raiz: o `.env` usava `AI_GEMINI_MODEL=gemini-flash-latest`, e o alias `-latest` passou a resolver para o **`gemini-3.6-flash`** (modelo novo, free tier de só **20 requisições/dia**). Bateu nas 20 e travou. NÃO era falta de crédito — era o apelido do modelo apontando para um modelo de cota minúscula.
**Decisão:** (1) Fixar `AI_GEMINI_MODEL` num id ESTÁVEL (ver entrada seguinte para a correção 2.5→3.5). Regra registrada no `.env.example`: NUNCA usar `-latest` (aponta para modelo volátil de cota imprevisível); preferir id fixo. (2) Fix estrutural mais importante — **escalonar-em-falha**: `AiReplyJobProcessor.process()`, no ramo `result.status !== 'success'` (cota, erro do provider, validação reprovada), antes só logava `warn` e a conversa ficava presa em `bot` em SILÊNCIO (cliente esperando para sempre, ninguém sabendo). Agora chama o novo método privado `escalateToHuman(tenantId, conversationId, reason)` — coloca a conversa em `'human'` sem dono (`assignedToUserId: null`), entrando na fila de "aguardando humano" (dispara o alerta/som/contador do N2) e parando a IA de tentar. O mesmo método é reusado pela auto-escalação da IA (N2), com `reason: 'decisao_da_ia' | 'falha_da_ia'` só para o log. Decisão do usuário: "escalar para um humano" em qualquer falha (não só cota) — nunca deixar o lead no vácuo.
**Impacto:** IA volta a responder com folga de cota grátis (custo zero; crédito na Anthropic só entra no futuro para um plano premium opcional). E, mais importante, qualquer falha futura da IA (cota, provider fora do ar, resposta inválida) agora VIRA um atendimento humano visível na Dashboard, em vez de silêncio. Testes: `AiReplyJobProcessor.test.ts` — os 2 casos de "resultado não enviável" passaram a exigir `status='human'`/sem dono; 10/10 verdes. tsc limpo (fora os 2 erros conhecidos de `aiBusinessProfile` até `prisma generate`). Só `.env`/`.env.example`/`AiReplyJobProcessor.ts`/teste tocados — fluxo de sucesso da IA e envio outbound intocados.

### Modelo Gemini para contas novas (404) + aviso educado antes de escalar + reativação do bot após silêncio

**Data:** 2026-07-23
**Contexto:** Sequência de três achados no teste real, todos na experiência do cliente: (1) `gemini-2.5-flash` devolvia **404 "no longer available to new users"** — a conta do usuário é nova e o Google bloqueou a linha 2.5 (o modelo aparece em ListModels mas o `generateContent` recusa). (2) Quando a IA devolvia resposta VAZIA (validação reprovada, 0 tokens de saída — típico de modelo "thinking" que gasta o orçamento no raciocínio) ou erro de provider, o cliente ficava no silêncio e a conversa sumia para a fila. (3) Uma vez escalada para humano sem dono, a conversa NUNCA voltava ao bot — se ninguém assumisse, o cliente ficava mudo para sempre.
**Decisão:** (1) **Modelo:** criado script de diagnóstico `apps/api/src/scripts/listGeminiModels.ts` (lê `GEMINI_API_KEY` do `.env`, lista modelos que suportam `generateContent` PARA AQUELA CHAVE — sem chute). Resultado: fixado `AI_GEMINI_MODEL=gemini-3.5-flash` (Flash estável da geração atual, disponível para contas novas, free tier ~1.500 req/dia). Também adicionado `AI_GEMINI_MAX_TOKENS=2048` (o default 1024 era consumido pelo "pensamento" do modelo e cortava a resposta visível). (2) **Aviso educado antes de escalar:** `AiReplyJobProcessor.sendHumanHandoffNotice()` — no ramo de falha, ANTES de `escalateToHuman`, envia ao cliente `DEFAULT_HUMAN_HANDOFF_MESSAGE` ("Desculpe, não consegui responder... encaminhando você para um atendente...") via outbound com `idempotencyKey` (mensagem do sistema, não `aiInteractionId`). Try/catch: se o envio falhar, escala mesmo assim (nunca bloqueia). NÃO afeta a auto-escalação por marcador (lá a própria IA já escreveu a despedida). (3) **Reativação do bot após silêncio:** nova policy de Domain `shouldReactivateBot` (`isWaitingForHumanUnowned` + silêncio `>= DEFAULT_BOT_REACTIVATION_SILENCE_MS`=30 min). `MessageIngestionService` ganhou 4º param opcional `botReactivationSilenceMs` (default 30 min) e, quando chega mensagem numa conversa aguardando humano SEM dono, mede o silêncio pelo `occurredAt` da última mensagem anterior (NÃO por `Conversation.updatedAt`, que o upsert bumpa a cada mensagem) e, se >= 30 min, devolve ao bot (`updateStatus('bot', {assignedToUserId:null})`) e agenda a IA para a mensagem que acabou de chegar. Decisão do usuário: gatilho "na próxima mensagem" + janela de 30 min de cortesia para o time humano (híbrido — evita o bot reassumir rápido demais e repetir o aviso de encaminhamento). Conversa COM dono (humano atendendo) nunca é reassumida.
**Impacto:** IA responde de fato (modelo válido) sem cortes; cliente nunca fica no silêncio ao falhar (recebe aviso e vira atendimento humano visível); e conversas abandonadas na fila voltam ao bot sozinhas na próxima dúvida do cliente, sem F5 nem ação manual. Multi-tenant intacto. Testes novos/ajustados: `AiReplyJobProcessor.test.ts` (11/11 — aviso enviado + resiliência do envio), `shouldReactivateBot.test.ts` (novo, policy pura), `MessageIngestionService.test.ts` (22/22 no conjunto — 2 testes de "escalada" viraram "com dono", +3 de reativação). tsc limpo (fora os 2 erros conhecidos de `aiBusinessProfile` até `prisma generate`). Wiring inalterado (params novos têm default). PENDÊNCIA: a instrumentação temporária `[OUTBOUND-DEBUG]` do diagnóstico do 463 ainda está ligada em `BaileysProvider` — remover quando a entrega estiver 100% estável.

### Retry automático em erro transitório do GeminiAiProvider (503 "high demand")

**Data:** 2026-07-23
**Contexto:** Mesmo com o modelo certo (`gemini-3.5-flash`), uma mensagem simples ("Olá") escalou para humano por causa de um `503 UNAVAILABLE` — "This model is currently experiencing high demand... usually temporary" (o próprio Google dizendo que era passageiro). A decisão original do projeto ("sem retry no provider, é responsabilidade do BullMQ") não cobria este caso: `ConversationAiService.generateReply()` CAPTURA a exceção do provider e vira um resultado `'provider_error'` — nunca relança —, então o job `ai-reply` nunca falha do ponto de vista do BullMQ; não havia re-entrega nenhuma a esperar.
**Decisão:** Retry movido para DENTRO do `GeminiAiProvider` (único lugar que conhece o `response.status` para diferenciar "vale tentar de novo" de "não adianta"). `RETRYABLE_STATUS_CODES = {500,502,503,504}` (servidor) + qualquer exceção que não seja um `GeminiHttpError` (o `fetchFn` lançando direto — falha de rede/timeout/DNS, retryable por padrão). Deliberadamente EXCLUÍDO: `429` (cota diária — retry em segundos não resolve, só atrasa o aviso ao cliente) e `404`/`401`/outros 4xx (erro de configuração permanente). Novo 6º parâmetro do construtor, um OPTIONS-OBJECT (`GeminiRetryOptions { maxRetries?, retryDelayMs?, sleepFn? }`, não mais 3 posicionais soltos — mesmo racional já usado na refatoração do `AiProviderFactoryImpl`) — defaults: 1 retentativa extra, 2s de espera (decisão do usuário), `sleepFn` injetável só para teste (evita esperas reais). Mensagem de erro final idêntica a antes (`"Gemini API respondeu <status>: <corpo>"`) — zero mudança de contrato para `ConversationAiService`.
**Impacto:** Instabilidades passageiras do Google (a maioria dos 503) agora se resolvem sozinhas em ~2s, sem incomodar o cliente nem gerar fila de atendimento desnecessária. Cota (429) e modelo errado (404) continuam indo direto para o humano — retry não ajudaria. `ClaudeAiProvider` NÃO recebeu o mesmo tratamento (YAGNI — não é o provider ativo hoje; o padrão pode ser replicado se/quando necessário). Testes novos: `GeminiAiProvider.test.ts` (13/13 — 503 recupera na 2ª tentativa, esgota retries e propaga, erro de rede recupera, 404 não retenta). tsc limpo. `AiReplyJobProcessor`/`ConversationAiService`/`AiProviderFactoryImpl` (34/34) intactos — wiring do `worker.ts` inalterado (defaults já são os recomendados).

### Milestone 6, Bloco M6H-1 — Arquitetura de navegação em dois níveis (Workspace × Sessão)

**Data:** 2026-07-24
**Contexto:** o fundador pediu uma reestruturação completa: hoje, logo após o login, toda a navegação (Dashboard/Conversas/Analytics/Usuários/Cérebro da IA) aparece de uma vez, antes de o usuário sequer escolher qual WhatsApp administrar — excesso de informação e modelo mental errado para um negócio com vários números. Pedido: Workspace limpo (nível 1, inspirado em Vercel/Stripe/Railway) e, dentro de cada WhatsApp, uma navegação própria (nível 2, inspirado em WhatsApp Desktop/Telegram/Intercom/Slack) — "cada WhatsApp é uma empresa independente".
**Levantamento de fatos no schema real, antes de desenhar** (ver ADR #74 para o detalhe completo): Conversas já têm `sessionName` no banco (escopar por sessão é trabalho de API, não migration — mas o filtro TEM que ser server-side, a paginação por cursor já documentada em `useConversationsList` proíbe filtro client-side); Cérebro da IA é 1:1 por tenant (`AiBusinessProfile.tenantId @unique`) — por sessão exige migration real; Analytics não guarda `sessionName` direto; Usuários são inteiramente por tenant, sem nenhum conceito de "por sessão".
**Decisão:** dois níveis. Nível 1 (`pages/index.tsx`) perde a `Sidebar` — vira só a grade de contas + botão de conectar; cada card ganha um indicador REAL (conversas aguardando atendimento naquela sessão, via `useWaitingForHuman.countBySession`, aditivo, zero endpoint novo) — indicadores sem dado real por trás ("quantidade de conversas total", "IA ativa") foram deliberadamente descartados por ora (inventar dado não é indicador). Nível 2: novo `SessionSidebar`+`SessionLayout` sob `/sessions/:nome/...` — Conversas, Cérebro da IA, Analytics, Equipe, Configurações, link de volta ao Workspace sempre visível. A antiga página de detalhe da sessão (QR/ações/histórico) virou a tela "Configurações" dentro desse layout, mesmo conteúdo. `Header` perdeu o título fixo "WhatsApp Automation Dashboard" (redundante, e agora o único lugar pra marca aparecer no nível 1) — vira `FrancisWordmark` compacta.
**Divergências do pedido, com justificativa:** (1) "Usuários por sessão" REJEITADO — fragmentaria o cadastro de funcionários numa PME com vários números (mesmo atendente em 2-3 sessões = cadastro duplicado + risco de esquecer de remover acesso); Equipe continua listando os usuários do TENANT, só mudou de lugar no menu. (2) "Analytics" mantém o nome (não virou "Insights" — termo mais reconhecível). (3) Pipeline de CRM NÃO entra neste bloco nem como maquete — sem o campo `stage` no banco seria simulação, não interface real; fica para M6H-5. (4) Cérebro da IA/Analytics/Equipe no menu da sessão hoje apontam para as páginas tenant-wide de sempre (ainda não escopadas) — limitação documentada em código, não bug: quem tiver 2+ WhatsApps vê o mesmo conteúdo nas duas sessões até M6H-3/M6H-4.
**Impacto:** zero migration neste bloco; zero contrato de API/BFF tocado. Testes novos: `SessionSidebar.test.tsx` (5 casos), `WhatsAppAccountCard.test.tsx` (+2, badge). `tsc --noEmit`/`npm run lint` limpos no sandbox; `dashboard-jsdom`/`next build` pendentes na máquina do usuário.

### Incidente crítico pós-M6H-2b: foto de perfil sem timeout travava o socket Baileys inteiro (Dashboard + WhatsApp real)

**Data:** 2026-07-25
**Contexto:** validado o Bloco M6H-2b (entrada anterior) na máquina real, o app travou por completo ao abrir qualquer conversa — Dashboard sem responder a cliques E entrega/recebimento real de WhatsApp parados, terminal da API preso em logs `"class":"baileys"`. Diagnóstico via as respostas do usuário às perguntas de triagem (acontece ao clicar numa conversa; nem UI nem WhatsApp real respondem).
**Decisão:** causa raiz era um bug introduzido no bloco anterior: `BaileysProvider.getProfilePictureUrl` consultava o socket Baileys ao vivo (`sock.profilePictureUrl`) SEM nenhum timeout — uma IQ query travada segurava a fila de IQ do socket inteiro, incluindo o tráfego de mensagens reais (o socket é compartilhado). Agravado por `ConversationInbox`/`ConversationDetailPanel` disparando várias buscas de avatar concorrentes e idênticas (lista + cabeçalho) sem deduplicação. Corrigido com `Promise.race` contra um timeout local de 6s (`PROFILE_PICTURE_TIMEOUT_MS`) — devolve `undefined` se estourar, a promise órfã ganha `.catch(() => {})` para nunca virar unhandled rejection. `hooks/useContactAvatar.ts` reescrito com deduplicação/cache em memória a nível de módulo (`Map`s por `sessionName:contactJid`).
**Impacto:** nenhuma mudança de contrato (o método já podia devolver `undefined`). Teste novo em `BaileysProvider.test.ts` (`jest.useFakeTimers()`). **Confirmado pelo usuário na máquina real** após reiniciar o terminal da API. Lição registrada: qualquer IQ query futura ao vivo do Baileys (`groupMetadata`, `onWhatsApp`, etc.) deve SEMPRE ter timeout — o socket nunca pode ficar refém de uma consulta auxiliar. Ver ADR #78.

### Reforma do escalonamento: a IA nunca mais tira a si mesma do circuito ao pedir ajuda humana

**Data:** 2026-07-25
**Contexto:** pedido do fundador — hoje, quando a IA não sabe responder ou decide encaminhar (marcador de escalonamento, feature N2), a conversa vira `status: 'human'` sem dono automaticamente, interrompendo `shouldAutoRespond()`; se ninguém assumir, o cliente fica sem resposta nenhuma, mesmo a perguntas simples que a IA saberia responder. Pedido explícito: a IA avisa o cliente que está encaminhando, a Dashboard é notificada, mas a IA CONTINUA respondendo enquanto ninguém assume — só uma ação humana explícita ("Assumir conversa") deve tirá-la do circuito. Duas clarificações confirmadas com o usuário (opção recomendada em ambas): a conversa permanece em `status: 'bot'` até ser assumida (sem status intermediário novo); uma escalada repetida na mesma conversa dispara um novo alerta, não só a primeira.
**Decisão:** novo campo aditivo `Conversation.escalatedAt?: Date` (migration `20260725120000_add_conversation_escalated_at`, nullable, sem backfill) — "a IA pediu ajuda pela última vez em X", independente de `status`. Novo método de port `ConversationRepository.flagNeedsHumanAttention(tenantId, conversationId, at)`: SEMPRE reescreve o timestamp, mesmo numa conversa já sinalizada (sustenta um novo alerta por escalada, não só a primeira). `UpdateConversationStatusOptions` ganhou `escalatedAt?: null` (mesma convenção de `assignedToUserId`: presença da chave decide se mexe; só `updateStatus` LIMPA, só `flagNeedsHumanAttention` GRAVA um `Date`). `AiReplyJobProcessor` (`escalateToHuman` renomeado para `flagNeedsHumanAttention`) parou de chamar `updateStatus(..., 'human', {assignedToUserId: null})` nos dois caminhos de escalonamento (marcador da IA E falha de geração/cota/provider) — agora só sinaliza; `status` nunca muda, a IA continua respondendo. `ConversationsService.escalateConversation`/`resumeConversation` (as ações reais de "Assumir conversa"/"Devolver ao bot") viram o ÚNICO caminho que muda `status`, sempre limpando `escalatedAt` junto. `findAllByTenant` ganhou `needsHumanAttention?: boolean` (`escalatedAt: { not: null }`), exposto via `?needsHumanAttention=true` (Zod `z.literal('true')`, não `z.coerce.boolean()` — evita `"false"` virar `true`) em `conversationsRouter`/BFF, substituindo o antigo filtro por `status: 'human'` sem dono. Frontend: `useWaitingForHuman` migrado para o novo filtro, com detecção de "nova escalada" por set-diff de chaves `id:escalatedAt` (não mais "o total subiu", que era cego a uma repetição na mesma conversa). `ConversationStatusBadge` ganhou prop `escalatedAt?` que sobrepõe o rótulo por "Aguardando atendente" independente de `status`; `ConversationListItem`/`ConversationDetailPanel` idem.
**Decisão de escopo:** `shouldReactivateBot`/reativação automática após 30min de silêncio (feature N2) ficou INTOCADA — vira rede de segurança só para linhas legadas com `status: 'human'` sem dono de antes desta reforma; estruturalmente inalcançável para escaladas novas (só `escalateConversation` grava `status: 'human'` agora, sempre com dono), mas manter o código testado não tinha custo, então não foi removido.
**Impacto:** nenhuma mudança de contrato pré-existente (tudo aditivo). Requer nova migration + `prisma generate` na máquina do usuário. Testes atualizados/novos: `AiReplyJobProcessor` (blocos de auto-escalonamento e "resultado não enviável" reescritos para `status: 'bot'` + `escalatedAt`, incluindo escalada repetida com timestamp mais recente), `ConversationsService` (+2), `ConversationListItem` (+2), `ConversationStatusBadge` (novo, 3 casos). `PrismaConversationRepository`/`conversationsRouter` seguem sem teste dedicado (padrão já estabelecido: validados por `tsc`/lint + cobertura indireta via `ConversationsService`/`AiReplyJobProcessor`). NOTA DE VERIFICAÇÃO: `tsc --noEmit`/`npm run lint` não puderam ser reexecutados no sandbox nesta rodada (ambiente isolado indisponível) — revisão manual linha a linha de todo o diff feita em substituição; validação real, suíte jest e `next build` pendentes na máquina do usuário. Ver ADR #79.

**Correções de acompanhamento, mesmo dia, após validação real:** migration aplicada com sucesso pelo usuário. `tsc --noEmit` (`apps/api`) achou 1 erro real: `validateOrRespond<T>(schema: z.ZodSchema<T>, ...)` não compilava para o novo schema `needsHumanAttention` (`.transform()` com tipo de entrada `"true" | undefined` diferente do de saída `true | undefined`) — corrigido generalizando a assinatura para `z.ZodType<Output, Def, Input = Output>` (retrocompatível, `Input = Output` é o default para todo schema sem `.transform()`). `npm run lint` achou 1 erro real: aspas retas em JSX em `ConversationDetailPanel.tsx` — corrigido com `&quot;`. Depois disso, usuário reportou que a ordem da lista de Conversas não refletia atividade recente (uma conversa reativada por escalada nova ficava presa embaixo) — `PrismaConversationRepository.findAllByTenant` ordenava por `createdAt`; corrigido para `updatedAt` (já é `@updatedAt` no schema, já tocado a cada mensagem/mudança de status — zero migration nova). Teste novo em `ConversationsService.test.ts` provando a inversão de ordem. Após todas as correções, `tsc --noEmit`/`npm run lint` confirmados 100% limpos pelo usuário nos dois pacotes.

### Status de conexão desatualizado no card do Workspace + bolinha de status em toda a navegação

**Data:** 2026-07-25
**Contexto:** usuário reportou (com prints) que o card "Seus WhatsApps" (Workspace) mostrava "Conectado" para uma sessão já desconectada de fato, enquanto a página de Configurações da mesma sessão mostrava "Desconectado" corretamente. Pedido adicional: uma bolinha verde/cinza de status, como já existe implicitamente na navegação por sessão, também no Workspace e no cabeçalho da sessão.
**Decisão:** causa raiz: `WhatsAppSessionService.listSessions()` (Workspace) sempre leu o `status` DIRETO do banco, por desenho desde a M2 — nunca passa pelo Registry, para não instanciar um `SessionManager`/socket Baileys novo por sessão só para listar. O banco só é atualizado de forma assíncrona enquanto existe uma instância viva daquela sessão no Registry (em memória); reinícios da API (vários nesta mesma sessão de trabalho, por travamentos do Prisma) deixavam o banco congelado no último status conhecido. Corrigido com um novo método `WhatsAppConnectionRegistry.peek(tenantId, sessionName)` — leitura pura do Map interno, NUNCA cria uma instância nova (diferente de `getOrCreate()`). `listSessions()` passou a, para cada sessão, tentar `peek()`: se achar uma instância viva, sobrepõe `status`/`phoneNumber` com o valor AO VIVO dela (`getStatus()`, mesma fonte de `getSessionStatus()`); sem instância viva, mantém o valor do banco como fallback — nenhuma sessão nova é instanciada só para listar (garantia original preservada). Novo componente `components/StatusDot.tsx` (bolinha verde/amarela/cinza, `role="status"` + `aria-label`/`title`, nova função pura `statusDotClassName` em `lib/formatters.ts` reaproveitando os tokens `success`/`warning` já existentes) aplicado em `WhatsAppAccountCard` e no cabeçalho da `SessionSidebar`.
**Impacto:** nenhuma mudança de contrato de API/BFF. **Data:** 2026-07-30

### Bug 2 (Pipeline travado), causa raiz real: `gemini-3.5-flash` com "thinking" ligado por padrão cortava o marcador de estágio

**Data:** 2026-07-30

### Pipeline: a IA reclassifica SEMPRE, mas nunca regride (trava por correção humana substituída por regra de direção)

**Decisão:** a proteção deixou de ser de POSSE e virou de DIREÇÃO. `shouldAiUpdateStage` reescrita de `(conversation) => stageSetBy === 'ai'` para `(conversation, suggestedStage) => STAGE_ORDER[suggestedStage] >= STAGE_ORDER[conversation.stage]`. **Impacto:** sem migration, sem mudança de contrato pré-existente. Testes reescritos: `shouldAiUpdateStage.test.ts` (11 casos), `AiReplyJobProcessor.test.ts` (caso de trava INVERTIDO + caso novo de regressão bloqueada), `ConversationsService.test.ts` (6 casos removidos com o método), `PipelineCard.test.tsx`/`PipelineColumn.test.tsx`. **NOTA DE VERIFICAÇÃO: a VM do sandbox caiu nesta rodada** — `tsc`/`eslint` não puderam ser reexecutados após as edições finais; revisão manual + `grep` confirmando zero referência órfã em código. ### Bug pós-F1.3: bolhas de mídia enviada pelo operador apareciam vazias na Dashboard (entrega real no WhatsApp funcionava)

Corrigido trocando a checagem para `row.mediaUrl != null && row.mediaKeyEncrypted != null` (aceita string vazia, só rejeita null/undefined); `mediaMimeType` continua truthy-check, pois nunca é gravado como `''` em nenhum caminho.

Investigação confirmou duas coisas: (1) a conversa misteriosa NÃO era um grupo nem um canal vazando — grupos (`@g.us`) já são filtrados desde a Milestone 3; era uma conversa 1:1 legítima (provavelmente `@lid`, comum em números novos) de um contato cujo `pushName` é um emoji, cortado ao meio pelo algoritmo de iniciais do avatar (`formatContactInitials` faz `word[0]` sobre um surrogate pair Unicode) — bug visual cosmético, não um problema de roteamento. (2) O filtro de grupo existente cobria só `@g.us` — canais/newsletters do WhatsApp usam o sufixo `@newsletter`, formato DIFERENTE, e não estavam cobertos: uma mensagem de canal passaria pelo filtro normalmente e criaria uma conversa com a IA respondendo dentro dela, o que não faz sentido (canal é transmissão de mão única).
**Decisão:** `BaileysProvider.handleMessagesUpsert` — condição de descarte estendida de `remoteJid.endsWith('@g.us')` para `remoteJid.endsWith('@g.us') || remoteJid.endsWith('@newsletter')`, mesmo ponto único de filtro (linha ~943), antes de qualquer extração de conteúdo/emissão de evento. Nenhuma mudança em `MessageIngestionService` ou qualquer camada além do provider — o filtro na origem já impede qualquer `WhatsAppConversation`/resposta de IA para esses dois tipos de endereço.
**Impacto:** fix de uma linha (mais documentação), nenhuma mudança de contrato/schema. Teste novo em `BaileysProvider.test.ts` (mesmo padrão do teste de grupo já existente, `remoteJid` terminado em `@newsletter`). `tsc --noEmit`/`eslint` confirmados limpos no sandbox. O bug visual do avatar com emoji cortado (`formatContactInitials`) fica registrado como item separado, não corrigido nesta rodada (cosmético, sem risco de a IA responder no lugar errado).

### Filtro de respostas/reações a Status (Stories) — segunda causa da "conversa sem origem clara"

**Data:** 2026-07-31
**Contexto:** mesmo dia do filtro de canal acima — o fundador reportou uma NOVA conversa (contato "Mathiaas ❤️") com um vídeo do TikTok, sem nenhum texto junto, e a IA respondendo normalmente a ela. Confirmado com o fundador que a mensagem era SÓ a mídia, sem nenhuma palavra escrita — padrão clássico de alguém reagindo/respondendo a um Status (Stories) do seu WhatsApp, não uma tentativa real de contato. Diferente de grupo/canal, essa mensagem chega com endereço 1:1 normal (`@s.whatsapp.net`/`@lid`), então os dois filtros anteriores não pegam.
**Decisão:** investigação direta no proto do Baileys (`WAProto/WAProto.proto`, pacote real instalado) confirmou um sinal confiável no próprio protocolo do WhatsApp: `ContextInfo.remoteJid` só é preenchido quando a mensagem citada mora num chat DIFERENTE de onde a resposta chegou (comportamento verificado em `lib/Utils/messages.js` do pacote). Ao reagir/responder a um Status, a mensagem original mora em `status@broadcast` (constante `STORIES_JID` do próprio Baileys) — logo `contextInfo.remoteJid === 'status@broadcast'` é o marcador. Novo tipo `BaileysContextInfo` (`{ remoteJid?: string | null }`) adicionado a `BaileysMediaMessage` (os 5 tipos de mídia) e a `extendedTextMessage`; nova função pura `isStatusReply(message)` checa esse campo em qualquer um dos 6 lugares possíveis. Filtrada no mesmo ponto único de `handleMessagesUpsert`, junto aos filtros de grupo/canal — decisão do fundador (via `AskUserQuestion`): ignorar completamente, sem criar conversa nem sinalizar de nenhuma forma (mesmo tratamento de grupo/canal), não uma opção intermediária de "registrar mas não responder".
**Impacto:** nenhuma mudança de contrato/schema. Testes novos em `BaileysProvider.test.ts`: resposta a Status em vídeo, resposta a Status em texto, e um caso de NÃO-regressão importante (uma resposta comum a outra mensagem do MESMO chat tem `contextInfo` presente mas SEM `remoteJid` — não deve ser filtrada; confirma que o filtro não bloqueia respostas/citações normais dentro da própria conversa). `tsc --noEmit`/`eslint` confirmados limpos no sandbox. **NOTA: este filtro está correto, mas NÃO era a causa do bug relatado** — o Status PUBLICADO chega por outro caminho, ver a entrada de HOTFIX abaixo.

### HOTFIX — Status (Stories) criavam conversas fantasma: filtro de `@broadcast` na origem

**Data:** 2026-07-31
**Contexto:** o fundador interrompeu a Fase 1 para reportar, como hotfix isolado (sem alterar o roadmap), que Status publicados por contatos criavam conversas na Dashboard, com a IA respondendo. Requisito: Status não devem gerar `Conversation`/`Message`/Pipeline/IA/Analytics/notificação — nada; e a correção deve ficar na origem, para o domínio nunca receber o evento.
**Duas tentativas anteriores erradas, registradas de propósito** (a lição da ADR #88 — "não acumular hipóteses sem medir" — se repetiu): o filtro de `@newsletter` (canais) e o `isStatusReply` (respostas/reações a Status) são ambos corretos em si, mas nenhum dos dois é o caminho pelo qual um Status PUBLICADO chega. As duas partiram de hipótese sobre o print; a terceira rodada começou lendo o protocolo e só então achou a causa.
**Causa raiz, verificada no FONTE do pacote instalado** (`@whiskeysockets/baileys@7.0.0-rc13`, não suposta): `lib/Utils/decode-wa-message.js` (~linha 150) monta a `key` de uma mensagem de broadcast com `chatId = from` e o autor real em `participant` — logo **um Status publicado chega com `key.remoteJid === 'status@broadcast'`** (e `broadcast: true` no nível da mensagem, campo documentado em `lib/Types/Message.d.ts`). O filtro de descarte cobria só `@g.us`/`@newsletter`, então isso passava; e como a conversa é chaveada por `contactJid`, **todos os Status de todas as pessoas colapsavam numa ÚNICA conversa** (`contactJid = 'status@broadcast'`), cujo `contactName` era sobrescrito pelo `pushName` do autor do último Status. Explica cada sintoma: uma só conversa "que aparece do nada", com nome mudando a cada print (Mathiaas ❤️ → Marcelo Santos → Juan Felipe → "."), sempre com mídia sem texto.
**Decisão:** nova função pura `isIgnoredChatJid(remoteJid)` no ponto ÚNICO de descarte de `handleMessagesUpsert`, filtrando por sufixo `@g.us`/`@newsletter`/**`@broadcast`** (este cobre `status@broadcast` e listas de transmissão — sufixo em vez de igualdade de propósito, pega qualquer broadcast presente ou futuro), reforçada por `message.broadcast === true` como defesa em profundidade. `isStatusReply` mantido, agora documentado como complementar (aquela mensagem chega no chat 1:1 normal, o filtro de sufixo não a alcança). Descartado filtrar em `MessageIngestionService` — contraria o requisito e faria o Application conhecer formatos de JID, responsabilidade do Provider.
**Achado colateral, NÃO corrigido (fora do escopo):** `key.senderPn` **não existe mais na v7** do Baileys (renomeado para `key.remoteJidAlt`), deixando o fix de LID da M6H-2b inerte. Registrado em `PRODUCT_BACKLOG.md` §2.
**Impacto:** nenhuma migration, nenhuma mudança de contrato/schema. Instrumentação `[STATUS-DEBUG]` do diagnóstico removida na mesma rodada (a causa foi confirmada por leitura do fonte, o log nunca foi necessário). Testes novos: 6 casos num `describe` dedicado em `BaileysProvider.test.ts` (Status em texto/imagem/vídeo, lista de transmissão, `broadcast: true` com `remoteJid` normal, e o caso de NÃO-regressão provando que mensagem privada legítima com `broadcast: false` continua passando). `tsc`/`eslint` limpos; `npx jest BaileysProvider.test.ts` **executado e VERDE no sandbox**. Novo script de limpeza `apps/api/src/scripts/cleanupStatusBroadcastConversations.ts` (modo simulação por padrão, `--apply` para apagar) — o filtro impede novas conversas fantasma, mas não remove a que já estava no banco. Nova oportunidade de produto registrada em `PRODUCT_BACKLOG.md` §1 ("Radar Social"), deliberadamente não implementada. Ver `DECISIONS.md` ADR #93.

### Revisão de UX: "Não é cliente" deixa de ser botão na conversa e vira coluna do Pipeline

**Data:** 2026-08-01
**Contexto:** horas depois de validar a ADR #94, o fundador usou a interface e recusou a UX do botão dentro da conversa, por argumento de operação real: num WhatsApp com centenas/milhares de conversas, marcar uma por uma não escala e faz perder o controle. ### Mensagens enviadas pelo operador de outro dispositivo (fromMe) passam a ser persistidas — Dashboard como espelho fiel do WhatsApp

**Data:** 2026-08-01
**Contexto:** mensagens enviadas pelo operador pelo WhatsApp mobile ou web (fora da Dashboard) nunca apareciam na Dashboard — a conversa só "nascia" quando o contato respondia. Causa raiz: `BaileysProvider.handleMessagesUpsert` descartava incondicionalmente todos os eventos com `message.key.fromMe === true`. A intenção era correta (evitar processar de novo os ecos das próprias respostas do bot), mas o filtro era excessivamente amplo — atingia também mensagens de outros dispositivos do operador, que não são ecos de nada.
**Decisão:** cache de IDs enviados por nós (`sentMessageIds: Map<string, Timeout>`, TTL 60s). Ao enviar via `sendMessage()`/`sendMediaMessage()`, captura-se o `key.id` retornado e armazena no cache. Em `handleMessagesUpsert`, para `fromMe: true`: ID no cache → eco do bot, já persistido → descartar (consome a entrada); ID fora do cache → operador enviou de outro dispositivo → emitir evento com `direction: 'outbound'`. Para eventos `outbound`, `from` usa `remoteJid` (o contato, endereço correto para chavear a conversa), nunca `senderPn` (que seria o próprio número do operador). `contactName` é omitido (o `pushName` de mensagens `fromMe` é o nome do operador, não do contato). Propagação em cadeia: `WhatsAppProviderEvent`/`InboundWhatsAppMessage` ganham campo `direction?: 'inbound' | 'outbound'` (undefined ≡ inbound — zero breaking change); `SessionManager` repassa; `MessageIngestionService` pula `incrementUnreadCount`, `maybeReactivateBot` e `aiReplyScheduler.schedule` para mensagens outbound.
**Impacto:** Dashboard passa a espelhar 100% do histórico real do WhatsApp (enviado/recebido, qualquer dispositivo). Sem migration, sem mudança de contrato de API/BFF. Testes: `BaileysProvider.test.ts` (+5: eco suprimido, fromMe-não-eco emitido como outbound, from=remoteJid, contactName omitido, eco de sendMediaMessage suprimido); `MessageIngestionService.test.ts` (+7: direction=outbound persiste, não agenda IA, não incrementa unread, cria conversa, omite contactName, não reativa bot, undefined≡inbound — 23/23 verdes no sandbox). `tsc --noEmit`/`eslint` limpos. ### Fase 1 — Botão POWER da IA (liga/desliga a resposta automática por sessão, sem afetar o WhatsApp)

**Data:** 2026-08-07
**Contexto:** pedido extenso e detalhado do fundador — um interruptor único por WhatsApp conectado que pausa SÓ a resposta automática da IA (não a conexão, não a ingestão de mensagens, não a Dashboard em tempo real, não o Pipeline/Analytics, não o envio manual do atendente), com persistência real no backend (não um estado só de frontend) e a garantia explícita de que religar não reprocessa retroativamente mensagens recebidas enquanto estava desligado.
**Decisão:** documentada em detalhe na DECISIONS.md ADR #99. Resumo: o estado (`aiEnabled: Boolean @default(true)`) foi anexado ao model já existente `AiBusinessProfile` (1:1 por sessão desde M6H-3) em vez de criar entidade nova — reaproveita a infraestrutura já pronta (rota por sessão, RBAC, UI). O bloqueio real acontece na função de Domain `shouldAutoRespond` (Milestone 3), que ganhou um terceiro critério `sessionAiEnabled`, checado nos DOIS pontos que já decidiam isso — `MessageIngestionService` (ao ingerir, decide se enfileira) e `AiReplyJobProcessor` (re-checa antes de gerar). Como a sessão desligada nunca ENFILEIRA o job, religar não tem nada pendente para reprocessar — cumpre o requisito sem lógica extra de "descarte de fila antiga". Nova porta estreita `AiAvailabilityRepository` em `services/conversations/domain` evita que esse bounded context importe o domínio inteiro de `services/ai` só para ler um booleano. Endpoint novo `PATCH .../ai-profile` (mesma permissão do `PUT` já existente). Botão minimalista (ícone Power, verde/vermelho) centralizado no `SessionHeader`. A pedido de acompanhamento do fundador, quando a IA está desligada TODO selo de status de conversa (lista, cabeçalho, painel de contexto) — inclusive conversas já com atendimento humano — passa a mostrar "IA desativada" em vermelho, sem exceção.
**Correção de acompanhamento, mesmo dia:** clicar no botão desligava a IA de verdade (confirmado pelo backend), mas os selos das conversas só refletiam depois de um F5 — causa raiz: cabeçalho e lista tinham cada um sua PRÓPRIA instância independente do hook de estado. Corrigido com `AiToggleContext` (Context React), montado uma vez em `SessionLayout`, compartilhado por todo consumidor da sessão — um clique atualiza tudo na mesma renderização.
**Impacto:** migration `20260807204225_add_ai_enabled_toggle` já aplicada nesta sessão (incluindo `prisma generate`) — nada pendente na máquina do fundador. Suíte completa do monorepo: 193 suítes / 1664 testes verdes (`tsc`/`eslint` limpos nos dois pacotes). Validado ao vivo no navegador, incluindo o fix de sincronização dos selos.

### Fase 1, Bloco F1.10 — Estabilidade e preparação para o beta fechado

**Data:** 2026-08-08
**Contexto:** antes de abrir um beta fechado para usuários externos, o fundador pediu uma auditoria técnica completa (arquitetura, segurança, performance, testes, documentação) e depois a correção dos itens P0 encontrados, numa única rodada disciplinada (analisar → implementar → testar → validar → checkpoint, item por item).
**Decisão (resumo — ver DECISIONS.md ADR #102 para o detalhe completo de cada item):**
- **Worker de `ai-reply`:** `concurrency: 5` (era o padrão do BullMQ, 1 — throughput global fixo baixo) + `KeyedMutex` (`shared/infrastructure/concurrency/KeyedMutex.ts`, mutex em memória por `tenantId:conversationId`) — paralelo entre conversas, serial dentro da mesma conversa, evitando duas respostas de IA conflitantes para o mesmo histórico.
- **Rate limit de IA:** `AiRateLimiter`/`InMemorySlidingWindowAiRateLimiter`, checado em `MessageIngestionService` antes de enfileirar — **6 tentativas/60s por conversa**, **30 tentativas/60s por sessão**. Estourou: nenhuma mensagem estranha ao cliente, só `flagNeedsHumanAttention` (mesmo alerta já existente para falha de IA) — recupera sozinho quando a janela desliza.
- **`GET /conversations/:id`** (API + BFF): elimina a varredura de até 1000 conversas por poll que `useConversationDetail` fazia antes; isolamento de tenant obrigatório (404 para conversa de outro tenant, nunca vaza dado).
- **Pop-up de handoff humano** (`ConversationHandoffPopup.tsx`): abre ao abrir uma conversa escalada e ainda não assumida, reusa `ConversationSummarySection` (resumo) e `escalateConversation` (assumir) sem reimplementar nada — fecha a lacuna encontrada na entrada de R5 acima.
- **Estabilidade menor:** índice `(tenantId, sessionName, lastMessageAt)` (migration `20260808120000_add_conversation_last_message_index`); `AgentMediaCache` isolado por tenant (era teto global de 500, agora 200 por tenant); upload de mídia no BFF com teto de 16MB aplicado DURANTE o streaming (não só no fim); validação de Content-Type por assinatura binária (`mediaMagicBytes.ts`, sem lib nova); teste de regressão para LID sem `remoteJidAlt`; teste flaky `formatElapsedDays` corrigido.
- **Testes reais contra infraestrutura real:** dois testes novos e pequenos (`postgresRealDb.integration.test.ts`, `aiReplyWorkerConcurrency.integration.test.ts`) — a suíte inteira do projeto sempre usou Fakes/mocks; estes dois provam os 2 pontos críticos desta rodada contra Postgres/Redis de verdade, sem substituir a suíte existente.
- **`GET /health/ready`:** novo, além do `/health` (liveness) já existente — checa Postgres/Redis/profundidade da fila de IA (`waiting`/`active`/`failed`/`delayed`), `200`/`503`. Sem métrica/dashboard novo, deliberadamente pequeno.

### Fase H — Prompt `v2` do Cérebro da IA: postura consultiva

**Data:** 2026-08-08
**Contexto:** `v1` era só anti-alucinação genérica, sem nenhuma instrução de venda/atendimento. O fundador pediu que a IA nunca ofereça serviço nas primeiras mensagens, entenda quem está falando e o que precisa antes de ofertar, nunca prometa aprovação, nunca incentive fraude/burla, converse naturalmente pelo WhatsApp, e evite respostas longas. Análise apresentada e aprovada ANTES de qualquer código, conforme pedido explícito.
**Decisão:** novo `v2` em `PROMPT_VERSIONS`, `v1` intocado (troca é só `AI_PROMPT_VERSION`, sem deploy de código para reverter). Estrutura: persona → postura consultiva (entender antes de ofertar, nunca repetir pergunta já respondida) → regras absolutas (herda "nunca inventar preço/prazo", adiciona "nunca prometer aprovação"/"nunca incentivar fraude") → brevidade → mídia + marcadores técnicos (estágio/escalonamento) extraídos para constantes compartilhadas, **textualmente idênticos** entre `v1`/`v2` — nunca reescritos do zero, para não arriscar quebrar o formato que Pipeline/escalonamento dependem. Ver DECISIONS.md ADR #103 para o detalhe completo.
**Limitação aceita:** a Base de Conhecimento continua um blob de texto livre único por sessão — "identificar o serviço certo" depende de como o texto foi organizado, não de catálogo estruturado. Resolver isso é mudança de schema, fora do escopo (só prompt, sem arquitetura nova, por instrução do fundador).
**Impacto:** zero mudança de schema/arquitetura. Testes novos: `PromptVersion.test.ts` (+8). `tsc`/`eslint` limpos. Suíte completa: 201/201 suítes, 1730/1730 testes verdes. Ativar `v2` em produção é decisão separada do fundador, não feita nesta rodada.
